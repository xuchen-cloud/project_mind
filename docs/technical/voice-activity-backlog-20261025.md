## 实际状态与复现

用户录音在 57,297 ms 自动暂停，持久化原因为 `activity_fault: recognition input has an audio gap`。原始麦克风和系统轨已保存约 57 秒，六段 Transcript 最后时间为 32,010 ms；本地识别还保存了同样的缺口错误。没有说话人分析任务，本机仅已准备 SenseVoice 模型。

此前 #253 只将识别队列改为按媒体进度消费，活动检测仍按近似相同回调次数读取两路。实际麦克风 48 kHz、每回调 1024 帧；系统轨 48 kHz 双声道、每回调 480 帧。两个队列都就绪时，系统轨的媒体进度容易落后，队列被占满后产生缺口并触发录音暂停。

以现有 1024 回调副本队列，在没有后台编译的条件下按采集速率回放同一音频：

| 对照 | 结果 |
| --- | --- |
| 仅 Activity | 57.298 秒、8356 回调全部通过，排空约 1 ms |
| Activity + LiveLocal、临时字幕开启，第一轮 | 52.814 秒副本队列背压，Activity 排空额外约 0.915 秒 |
| 同一并行路径，第二轮 | 53.074 秒 **System** 队列背压，Activity 排空额外约 1.101 秒 |

单独检测能够跟上，两个并行消费者时系统副本稳定积压。原始录制末段曾与编译重叠，负载会放大问题，但空闲回放已排除“仅由那次编译导致”的解释。

## 性能对照与修复范围

本机为 M1、8 核、8 GB。使用相同前 15 秒麦克风样本、500 个 30 ms 检测帧，直接降采样并绕开 Track 来隔离推理开销：

| 后端设置 | 总耗时 | 实时比 | 单帧 p95 / 最大值 | 检测语音帧 |
| --- | --- | --- | --- | --- |
| 原默认线程 | 7.581 秒 | 0.505 | 61.625 / 76.053 ms | 244 |
| 独立测试进程单线程 | 20.615 秒 | 1.374 | 158.916 / 232.258 ms | 244 |
| 系统 Accelerate、默认线程 | 0.981 秒 | 0.065 | 7.727 / 9.030 ms | 244 |

系统轨在该样本中为静音，500 帧耗时约 0.006 秒。单线程实测更慢，未作为产品修复；没有修改应用全局线程环境变量。

活动检测复用识别的真实双轨消费器，按每轨累计媒体进度优先读取落后轨；每次 VAD 排空缓冲后仍使用累计位置，单轨 EOF 后继续排空另一轨。macOS 为当前固定版本 Candle CPU 运算启用系统 Accelerate BLAS；FSMN 模型、阈值、采样、窗口和分段规则保持不变，Windows 依赖配置保持不变。

同一检测输入在加速后约快 7.7 倍，354 个有能量支持的帧与 244 个语音判定帧均与原结果一致；没有通过静音、降采样率或放宽阈值换取速度。
