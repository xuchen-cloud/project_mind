## 一手证据：模式与工具分别负责什么

Karpathy 的 gist 是设计模式，并非可安装软件；本次仅采用作者正文，评论中的第三方实现、宣传和效果主张没有当成作者实现。正文提出原始来源、关联 wiki、维护 schema 三层：先积累可复用理解，再查询；`index.md` 提供链接和一句话描述，回答时先读索引再进入相关页面；`log.md` 记录时间线。`ingest` 整合来源，`query` 带引用回答并沉淀有价值发现，`lint` 检查过时、矛盾、孤立页和缺失关联。作者允许批量摄入，但未规定夜间调度或增量游标算法。来源：[原始正文](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。

qmd 是作者推荐的可选检索工具，提供 CLI 与 MCP；关键词、向量和混合重排是可选检索路径，不是 wiki 维护器。它没有替 Mind 管理会话摘要、项目概览或 Workspace 长期记忆。其 README 也提示默认 embedding 对中文覆盖有限，需要选择模型并重新索引。来源：[官方 README](https://github.com/tobi/qmd/blob/04e4dbd8245c527a88f1a8f0bda547aef9ca81fb/README.md)。

## qmd 实现中可直接借鉴的接口

| 已核实行为 | 对 Mind 的启发 |
| --- | --- |
| 初始化描述仅列文档总数、集合名称等入口，详细情况通过 `status` 获取。 | 开会话先给小入口，不加载全部目录和正文。 |
| MCP `query` 返回文档 ID、标题、context、命中行和片段；说明中指引按命中行调用 `get`。 | 候选发现与实际阅读分开。 |
| `get` 支持 `fromLine/maxLines`；`multi_get` 支持批量读取及逐文件大小限制。 | 显式提供局部读取和有限批量读取。 |

以上依据：[src/mcp/server.ts](https://github.com/tobi/qmd/blob/04e4dbd8245c527a88f1a8f0bda547aef9ca81fb/src/mcp/server.ts) 的 `buildInstructions`、`query`、`get`、`multi_get`。当前源码 `query`/`searches` 二选一；`multi_get` 默认 65,536 字节。README 的 MCP 参数表有漂移。`get` 未指定范围仍可全文返回，逐文件上限也不是整轮 token 上限；不能声称 qmd 已强制实现预算控制。

CLI JSON 默认输出片段，`--full` 才改成正文；`--files` 可只返回标识、分数、路径和 context，给 Agent 一个更轻的候选清单。来源：[src/cli/formatter.ts](https://github.com/tobi/qmd/blob/04e4dbd8245c527a88f1a8f0bda547aef9ca81fb/src/cli/formatter.ts)，`searchResultsToJson/searchResultsToFiles`。

MCP 调用片段提取时传入 300 字符限额；提取实现限制片段正文后再加位置头部，因此不是整个响应严格只有 300 字符。context 实现合并全局及所有匹配路径前缀的描述，与 README“最长匹配”措辞不同。其价值是说明内容用途，不等于自动维护的项目知识。来源：[src/store.ts](https://github.com/tobi/qmd/blob/04e4dbd8245c527a88f1a8f0bda547aef9ca81fb/src/store.ts)，`extractSnippet/getContextForPath`。

官方 skill 要求事实、决定、引文和细微差别不能仅依据检索片段作答；同时提供命中附近的行范围读取。它建议由 Agent 根据意图编写查询，并在语义检索失败时退回关键词检索。应借鉴“核实相关原文”，不把它误解成“每次读取整篇”。来源：[官方 qmd skill](https://github.com/tobi/qmd/blob/04e4dbd8245c527a88f1a8f0bda547aef9ca81fb/skills/qmd/SKILL.md)。

## 对 Mind 的建议：知识维护与问题检索分开

以下均是基于用户目标的 Mind 设计建议，不是对 gist 或 qmd 的功能描述。

### 1. 持久化知识层，而非更长的首轮 prompt

Project Overview 保存项目目标、阶段、重要决定、未解决问题，以及能够进一步阅读的主题、Record、Voice Record、File、会话摘要入口。它既有简短理解，也有导航；完整对象清单另设分页索引。Overview 不应随资料增长无限变长。

Workspace Overview 汇总 Project Overview 的变化和 Workspace 自有知识，长期记忆区分明确偏好、长期关注和临时意图。项目级会话不得因为使用相同 Agent 而自动加载整个 Workspace 或其他 Project。

主题页承载跨来源理解，来源摘要承载单份资料的提要，会话分段摘要承载讨论经过。它们不应全部塞进 Overview，也不应自动复制为用户可见 Record。需要作为工作成果使用时，再创建或关联现有 Record。

### 2. 新会话按问题渐进展开

建议的阅读路径如下；这是可跳过层级的策略，不是每题必须走完的流水线。

1. **入口**：当前作用域、精简 Overview、更新时间/未合并变化提示、可调用工具说明。
2. **定位**：根据用户问题选择 Overview 中相关链接，或检索主题、资料和会话摘要；只返回有限数量的标题、说明、来源时间、版本和定位锚点。
3. **理解**：读取相关主题段落、文档摘要或会话分段摘要；确认问题还缺哪类证据。
4. **核实**：仅取相关原文块、会话消息窗口或 Voice Transcript 时间段；保留所属版本。
5. **扩大**：用户要求全文总结/改写、需要跨章节关系、片段不足或来源冲突时，才读取完整目标或连续分页。
6. **停止**：问题所需结论已有可定位证据，且没有未解决的相关冲突，就作答并引用；不为填满预算继续搜。

用户已指定某条 Record、File 或会话时可直接读取它，无需先绕一遍所有概览。导航缺失、概览过期或新内容尚未合并时，允许绕过 wiki 层检索当前原始来源。找不到不能推出“项目里没有”。

例如“上次为什么暂缓权限管理”：Overview 的决定入口 → 相关会话分段摘要 → 用户作决定及其前后消息 → 带会话锚点回答；不用读取所有历史会话，也不用读取那次长会话全文。

### 3. 窄接口与服务端预算

建议领域服务提供五类能力，GUI、CLI、MCP 和内置 Agent 共享语义；具体命名以开发规格为准：

| 能力 | 最小返回内容与约束 |
| --- | --- |
| 读取概览 | 短正文、版本、覆盖到的变更序号、dirty 状态、下钻入口；不自动带所有子项目概览。 |
| 查询索引 | 有限候选、导航说明、对象类型、摘要版本、最新源版本、片段/锚点；不夹带全文。 |
| 读取摘要/目录 | 指定对象或主题的摘要与章节入口，标记其依据和覆盖范围。 |
| 读取原文 | 指定 block/message/time range，返回精确 revision、实际覆盖范围、截断状态和下一页游标。 |
| 展开关联 | 有限一跳引用和反向链接，显式页数/条数；不递归加载全部图谱。 |

预算至少涵盖每次工具返回和整轮累计读取。由服务端执行 `limit`、字符/字节及 token 估算限制，返回 `truncated/hasMore/nextCursor`；不能只在提示词中要求“少读”。总预算需预留当前问题、工具协议、推理和最终回答空间。缓存按对象 revision 去重，内容未变化时不重复加载。批量读取必须限制总量，不能只有单文件上限。

候选页/摘要只用于决定下一步阅读；重要决定、精确引文、冲突判断和正文修改，应核实对应源版本。即使允许直接回答概览型问题，也应明确回答依据是派生理解及其覆盖时间，而不是伪装成实时完整事实。

### 4. 夜间增量维护不能反复摘要漂移

写入时只做便宜的变更登记和来源索引更新；昂贵的跨来源理解按天/隔天合并。每 Project 使用已消费游标到本次截止游标的变更集合，读取旧 Overview、受影响摘要和必要源片段；同一对象多次修改合并到本次目标版本。生成后验证引用及源版本，再提交新 Overview 并推进游标；失败不推进，重试不重复归纳。新写入落到下一批。

变更必须包含删除、撤回、来源移动、版本恢复和会话新分段，不能只监控“新文件”。处理受影响的主题与引用链，保留未受影响知识。Workspace 在相关 Project 更新完成后消费其新版本，同时处理 Workspace 自有来源。

不能永远只把“旧摘要 + 新摘要”再总结：需要定期或按异常触发 lint，回查支撑关键主张的源片段；标记失效引用、相互矛盾、长期未核实和来源丢失。原来重要但长期未动的 Todo 可以被标为待复核，但不能仅凭年龄判为不重要或自动完成。

## 不照搬的边界与待验证项

- **原始内容可修改**：gist 的不可变 raw 假设不能直接套用。Mind Record 和 File 可版本化编辑，因此引用、摘要和概览都必须记录源版本及失效关系；Transcript 保持现有领域语义。
- **SQLite 是主存储**：无需为了 wiki 目录新增第二套权威 Markdown 库；可把可读 Markdown/JSON 作为 CLI/MCP 的投影或导出。
- **中文检索独立评测**：qmd 有 CJK 归一化回归测试，但测试存在不等于 Mind 中文访谈、混合术语、简称和历史决定问题的召回保证。来源：[官方 CJK 测试](https://github.com/tobi/qmd/blob/04e4dbd8245c527a88f1a8f0bda547aef9ca81fb/test/store-cjk-fts.test.ts)。
- **不立即绑定 qmd**：先实现领域接口和分层读取约束，关键词/中文分词建立基线；再用同一问题集比较语义检索与重排的收益、延迟、内存和打包成本。是否采用 qmd 是后续选型，不是本次研究结论。
- **schema 与资料分开**：维护规则由应用配置提供；资料或会话里出现的指令只是可检索内容，不能改变作用域、权限或维护流程。

验收应同时看“回答正确”和“读得克制”：每题记录实际读取对象/版本/层级、累计字符或 token、引用落点、检索耗时和回退原因。样例应覆盖精确标题、模糊历史问题、旧结论被推翻、最新内容未进 Overview、超长会话、过期摘要、无答案、跨项目权限和全文改稿；不能只测“概览有没有生成”。
