# 长期记忆实施说明

状态：2026-10-09，S7 本地实现及有效验证完成；真实模型与目标平台验收尚未完成。对应 [S7/R14c 工作包](../requirements/ai-work-context-delivery.md)和 [Hermes 固定版本源码参考](hermes-memory-reference.md)。Workspace 分层知识由 S6 提供；这里复用它的来源证明、知识正文与版本。

## 用户会看到什么

助手把有长期价值的信息整理成少量条目，例如工作背景、常用方法和明确偏好。用户可以在知识面板查看依据，确认、纠正、停用或重新启用。模型整理出来的条目先标为推断；不能因为重复出现，或经过多次摘要，就变成“用户已确认”。

停用表示这类记忆不再参与助手上下文和记忆检索。原始讨论、Record 和项目资料仍然存在，也可以单独搜索。操作说明要明确实际范围：同一工作范围、同类记忆、相同原始来源。不能把这种按来源抑制说成已经从所有文字中识别并抹去了同一含义。

项目归档后保留已有条目和版本，展示来源状态；保留记录不代表模型仍有权读取。Project 助手不自动带入 Workspace 的个人记忆。

## 借鉴 Hermes 的部分

Hermes 将短记忆与可检索会话历史分开，模型通过明确的写入动作维护条目，修改旧条目时固定目标。ProjectMind 沿用这三个思路：短记忆只放稳定信息，原话按需回读，用户操作指向具体条目及版本。

ProjectMind 不直接照搬两份全局 Markdown 文件。已有知识节点、不可变版本和检索可以承载正文；Workspace/Project 授权及来源失效仍由原生服务执行。Pi 压缩解决当前对话放不下的问题，不代替长期知识，也不作为可信引用。Hermes 的删除工具不等于已经解决 ProjectMind 所需的派生失效与停用后防止重新生成。

## 最小实现路径

1. 在现有知识节点中标识长期条目。类别沿主规格使用 `background`、`domain`、`interest`、`method`、`preference`、`knowledge_pointer`；保存适用范围、支持时间和状态，不新增另一份正文库。
2. 在现有维护生成结果中接收候选，复用本次实际读到的原文或项目概览证据索引。模型不能自行声明可信来源、支持时间或用户确认。发布与本批水位、进度一起提交。
3. 原生服务独立保存用户的确认、纠正和停用策略。确认绑定用户实际看到的节点版本；纠正写入既有知识版本历史，并保留依据。模型维护不能覆盖这些用户决定。
4. 停用同时保存按原始来源身份及记忆类别建立的抑制记录。后续模型即使换标题或节点 ID，命中的候选也跳过；其他有效候选照常发布。多来源条目只要命中其中一个受抑制来源，就不能靠删掉那条引用继续发布同一候选。
5. 默认上下文只提供现有预算内的稳定记忆入口，更多内容沿知识检索和历史回读获取。条目被停用、纠正或失去来源权限后，知识检索、旧版本读取和后续模型会话中的相关派生内容都要遵守最新状态。

用户操作和后台发布之间使用已有版本检查。后台开始后若用户改变了记忆策略，旧草稿不能覆盖新决定；重新准备该批时应用新策略，不能无限重试一个已经失效的草稿。重新启用是用户的明确操作，并不自动使过时依据恢复有效。同一来源被多个停用决定覆盖时，重新启用一条只撤回它自己的决定，不能顺带解除另一条仍有效的停用；面板应说明由哪条决定影响当前条目。

## 会话中的旧记忆

只保存原始来源依赖还不够：停用一条记忆时，原始 Record 可能完全没有变化。如果后续会话只检查 Record 是否可读，就会重新带入先前读过的记忆。实现已在现有 Run 来源账本中同时记录实际读过的记忆条目、版本和用户策略证明；继续对话和引用旧讨论时复核它。原文依赖仍完整保留，不能用记忆条目替代原始依据，也不能把记忆伪装成新的原始文件。沿现有账本和读取边界完成，不新增一套会话存储。

## 实施顺序与接口边界

S7 依赖 S6 的分层来源读取，按下面的顺序收口；明确的实现任务交给 GPT-6 Sol，主 agent 负责接口定案和最终检查。

| 步骤 | 实际交付 | 验证重点 |
| --- | --- | --- |
| 存储与用户操作 | 为既有知识节点增加记忆元信息；用户策略与抑制记录独立保存。GUI 可分页查看、确认、纠正、停用及重新启用。 | 升级旧库、版本冲突、重开后策略保留、多项停用互不误解除。 |
| 增量提取 | 既有维护任务接收模型候选，绑定实际读取的来源；与概览、水位和草稿一起保存。 | 推断不能自称确认；受保护或受抑制候选跳过，其他条目继续；恢复草稿不重复调用模型。 |
| 读取与会话依赖 | 知识读取、检索、入口与 Run 来源账本共同遵守当前记忆策略及来源授权。 | 停用、纠正、撤权后，旧知识版本和模型历史不重新带回失效记忆；混合来源不泄露。 |
| 界面与交付核对 | 现有知识面板显示类别、确认状态、依据和操作结果；文档区分已实现与真实模型待验。 | 操作绑定所见版本，切换 Workspace 不串数据；相关前后端检查与主 agent Standards/Spec 检查。 |

用户纠正继续使用既有知识版本，并保留该条目原来真实的概览发布基线；用户策略另有自己的版本，不能为一次手动修改伪造概览发布。GUI 管理入口可以展示停用或归档条目的保留状态，但它与模型读取入口分开：用户能管理记录，不代表模型重新获得来源权限。

管理入口采用三个原生命令：分页列表、单条详情、更新操作。更新只包含确认、纠正、停用和重新启用，携带用户所见的条目版本与策略版本。停用策略的归属就是作用域加条目 ID；重新启用只撤回该条自己的抑制记录，不增加一套供客户端管理的“停用事件 ID”。

条目分别显示确认程度（推断或用户确认）、启用状态和依据状态（当前、已变化、不可用或归档）。这些含义不同：重新启用一个归档条目不会让它重新进入模型上下文。GUI 可以管理其启停状态；确认需要当前有效依据，纠正可以针对已变化但仍可读取的依据。详情复用已有原始来源与项目概览来源字段，不另造来源格式。

## 验收重点

- 从真实来源形成候选，模型不能凭空写出“用户已确认”。
- 纠正生成可追溯版本；下一次后台整理保留用户修正。
- 停用后重新打开软件、换标题、换节点 ID，下一批都不会从同一依据恢复同类条目；重新启用后按当前依据处理。
- 只授权部分项目时，混合来源结论整体不可见；来源删除、排除或归档后的状态如实呈现。
- 旧知识页面、关联入口与模型可用历史不会绕过停用或来源权限；用户自己的历史记录仍按既有查看规则保留。
- 无变化不增加生成调用；保存草稿恢复不重复计费，策略已变化的草稿不能覆盖用户决定。

这些是 ProjectMind 自身的验收要求，不能用 Hermes 上游测试或本设计文档代替执行结果。实际命令、结果和仍需真实 Provider 验证的部分已登记在[交付台账 S7/S8 段](../requirements/ai-work-context-delivery.md)。

## 当前实现落点

后台复用既有概览维护的一次模型响应，通过可选 `memoryCandidates` 返回候选；没有额外创建记忆审阅 worker，也没有新增每日调用次数上限。模型选择类别、内容和本次读取的证据索引，原生端生成条目身份、来源与版本。与 Hermes 直接调用 `memory` 工具不同，这里的写入沿现有概览发布事务完成。相同类别与同组依据合成一个条目，后续分页会携带其已有内容；用户确认或纠正的条目作为只读上下文提供。候选即使引用项目概览，也必须能展开到原始来源。

正文仍在 `agent_knowledge_versions`，当前指针增加 `memory` 类型；schema 37 增加用户策略、原始来源抑制与索引、策略版本表。GUI 的列表、详情与更新通过 `agent_memory_list/get/update`，每次修改携带所见条目及策略版本。默认 Workspace 上下文在已有八个入口和字符预算内优先给出记忆导航，完整内容按需读取；推断与用户确认在入口中有明确标识。

Run 账本同时保存原文、记忆版本及用户策略版本、项目概览条目证明。停用、纠正或父概览失效后，即使原文仍可读，旧派生内容也不能仅靠原文授权重新进入模型。重新启用后需要新的有效读取；原先失效的 Run 证明不会自动恢复。

本轮浏览器夹具使用真实 React 组件与模拟 IPC，在 736/1200 像素宽度验证了按需读取、纠正、停用/重新启用、切换工作区、滚动和焦点。发现并修复了记忆长列表的滚动高度问题。它不代替原生 Tauri 或真实 Provider 验收；最终后端和前端证据统一记录在交付台账。
