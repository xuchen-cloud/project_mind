# Project Mind 帮助中心写作计划

状态：规划稿 v2
更新时间：2026-08-21
文档基线：`9b359e83e76bf35bee7d46a9a97659af3916f784`，见第 7 节

## 1. 本轮审视结论

现有计划已经抓住了 flomo 帮助中心最值得借鉴的部分：按用户任务组织、把“怎么做”和“为什么做”放在同一体系中、主动说明边界，并让截图紧跟操作点。问题主要不在选题缺失，而在交付结构、首发范围和执行约束。

| 问题 | 影响 | 本轮调整 |
| --- | --- | --- |
| 计划要求“一篇解决一个问题”，却把 30 个文章单元合并成 8 个长文件 | 搜索结果只能落到长页，链接和维护粒度过粗，也偏离 flomo 的“栏目 → 独立文章”结构 | 改为“栏目目录 + 独立文章”；一篇文章只保留一个主要用户任务 |
| 30 篇内容同时开写，没有 P0/P1/P2 | 首发周期长，核心帮助内容会被方法文章、低频设置和视觉制作阻塞 | 分三阶段发布，先交付 15 篇 P0 核心文章 |
| 目录虽然以任务命名，逐篇概要仍混入较多功能清单 | 单篇容易变成“把所有按钮都写进去”，用户结果不够突出 | 每篇先定义用户问题、完成结果和退出路径，再决定覆盖哪些功能 |
| “10 分钟上手”覆盖创建、组织、沉淀和行动，但没有明确的成功画面 | 用户可能走完步骤仍不知道自己获得了什么 | 把首个闭环定义为“接住一段信息 → 留下一条可找回的 Record → 建立一个下一步 Todo → 再次找到它们” |
| 两条价值主线写得过于技术化，尤其强调 Markdown / HTML 双表示 | 容易把实现细节变成用户承诺，也抢占操作正文 | 只表达可观察结果：“粘贴后结构仍可编辑”“按用途导出”；内部表示仅在确有必要时说明 |
| 交叉链接只有原则，没有逐篇链接责任 | 写完后仍可能形成孤岛 | 每篇强制设置“上一级、下一步、相关方法”三类链接，并在验收时检查双向关系 |
| 截图与生成图预算过大，且在正文稳定前预先指定 | 截图会快速过期，视觉制作可能反过来决定文章结构 | 先完成无图可读稿；仅在位置、状态差异或空间关系无法用文字说清时配图 |
| “当前代码与测试”没有绑定到确定版本 | 开发中或未发布能力可能进入正式帮助文档 | 写作前锁定 release/tag/commit，并为高风险事实保留证据与复核日期 |
| “一篇文章一个全新 agent”会切断同一用户旅程的上下文 | 术语、案例和前后步骤更容易漂移，编辑阶段成本高 | 改为按用户旅程成组写作，同组共享事实表与示例；再做跨组编辑审校 |

因此，本计划不再以“覆盖所有功能”为首要完成信号，而以三个结果为准：新用户能完成第一次闭环；搜索访问者能直接落到答案；每项公开承诺都能追溯到已发布产品事实。

主要研究：[flomo 帮助中心结构与文章模式调研](../research/flomo-help-center-structure.md)。补充样本与写法归纳见[信息架构与内容模式分析](../research/flomo-help-center-analysis.md)。

## 2. 目标、受众与编辑原则

### 2.1 要回答的用户问题

1. 我第一次打开 Project Mind，怎样尽快用起来？
2. 一段信息或一个行动应该放在哪里，之后怎样找回来？
3. 我怎样让一个 Project 的判断、Todo 和 File 保持在同一上下文中？
4. 哪些数据留在本地，哪些内容可能发送给 AI Provider？
5. 出现异常或看不到内容时，我应该先检查什么？

### 2.2 主要受众

- **第一次使用者**：需要最短成功路径，不应先学习完整领域模型。
- **带着问题来的使用者**：从搜索或错误现场进入，需要第一段就得到结论。
- **已经稳定使用的人**：需要作用域、连接方式、数据边界和工作方法。

### 2.3 编辑原则

- **按任务组织**：一级栏目表达用户要完成的事，平台差异下沉到文章内部。
- **答案先行**：FAQ、边界和排障页第一段直接给结论，然后补原因、例外和下一步。
- **先结果后机制**：先说明用户会获得什么，再解释按钮和产品机制。
- **一次只解决一个主要问题**：复杂主题拆成独立文章，不依赖超长页内锚点维持可读性。
- **功能与方法互链**：操作页回答“怎么做”，场景页回答“何时这样做更合适”。
- **作用域必须明确**：涉及 Record、Todo、Tag、File 和 Internal Reference 时，说明它属于 Workspace 还是某个 Project。
- **边界公开**：明确 Archive 不等于完成、QuickNote 不是长期存档、Record Export 不是 Workspace Backup、AI 结果不会自动成为 Committed Content。
- **沿用正式领域词**：遵守 [`CONTEXT.md`](../../CONTEXT.md)，不用“笔记”“任务”“附件”等近义词替换正式对象名。
- **不复制 flomo 表达**：借鉴信息组织和编辑机制，不复制其口号、案例、emoji 体系或产品概念。

## 3. 信息架构与文件结构

采用接近 flomo 的浅层结构：**首页 → 栏目 → 独立文章**。栏目负责导航，文章负责回答一个问题。正文原则上不超过三级标题。

```text
docs/help/
├── README.md
├── getting-started/
├── capture/
├── context/
├── momentum/
├── thinking-with-ai/
├── workflows/
├── trust-and-help/
└── assets/
```

每个栏目目录包含一个 `README.md` 作为栏目入口，以及若干独立文章。最终文件数不再人为限制为 8；独立 URL、独立标题和独立维护责任比文件数量更重要。若未来发布器不支持目录页，再在构建层合并，不在源文档层牺牲文章粒度。

第 4 节的文章清单是导航、栏目入口和上一篇/下一篇顺序的单一权威来源；不另行手写一份与之并行的全量 `SUMMARY`。面向搜索访问者的推荐路径是“FAQ/排障先命中 → 操作页完成任务 → 场景/方法页建立长期用法”。

首页只承担四件事：一句话定位、10 分钟上手入口、按任务找答案、适合与不适合的边界。两条核心价值用用户可验证的结果表达：

- 写入或粘贴有结构的内容后，仍能继续编辑，并可按用途导出一条 Record。
- Project 的 Record、Todo 和 File 可以留在同一工作现场中，之后按作用域、Tag、搜索和连接找回。

## 4. 文章清单与发布优先级

优先级含义：

- **P0**：首发必需，覆盖第一次闭环、高频找回、核心边界和主要故障。
- **P1**：补齐高频能力和进阶操作。
- **P2**：方法、个性化与低频参考；不得阻塞首发。

## 5. 单篇文章 brief 与写作模板

每篇动笔前先填写以下 brief；缺少“用户问题”或“完成结果”时不得开始堆步骤。

```text
文章：
类型：上手 / 操作 / 决策 / 场景 / FAQ / 排障
目标读者与前置条件：
用户原话式问题：
读完后的可观察结果：
必须核验的产品事实：
明确不覆盖的内容：
需要的视觉（如无则写“无”）：
上一级 / 下一步 / 相关方法链接：
```

### 5.1 上手与操作文章

1. 用一小段说明完成后会得到什么。
2. 写清前置条件。
3. 用编号步骤完成一条线性任务，每一步同时写动作与可观察结果。
4. 仅在决策点放截图或技巧。
5. 说明作用域、限制、数据风险和不可逆动作。
6. 用“接下来”链接到自然的下一任务。

### 5.2 决策、FAQ 与排障文章

1. 标题或小标题复述用户问题/现象。
2. 第一段直接给结论。
3. 解释原因、例外和当前边界。
4. 排障按“最常见且最安全 → 较少见 → 需要进一步帮助”排序。
5. 给替代路径或准确的下一篇链接。

### 5.3 场景与方法文章

1. 从一个真实困境开始，不虚构用户证言。
2. 先给可执行判断原则。
3. 用同一个示例沿工作过程展开。
4. 操作细节链接到功能页，不在方法页重复整套步骤。
5. 用一句可以复用的做法收束。

### 5.4 语言规范

- 直接称呼“你”，短句优先，友好但克制。
- 界面文字使用中文引号；命令、快捷输入和路径使用行内代码。
- 标题优先使用真实问题或动宾结构，不用内部模块名充当用户标题。
- 首次出现正式领域词时用一句话解释，后文保持同一词汇。
- 不使用“永远”“完全不会丢失”“只发送选中文字”等无法严格成立的承诺。
- 限制应同时说明影响和可行替代方案，避免只写“暂不支持”。

## 6. 导航、视觉与可维护性

### 6.1 链接规则

每篇文章至少包含：

- 一个栏目入口链接；
- 一个自然的“接下来”链接；
- 0–3 个真正相关的深链，不堆“猜你喜欢”；
- 方法页与其主要功能页之间的双向链接。

栏目页按“从这里开始 / 完成核心任务 / 进一步了解”排列，不按文件名字母顺序。首页与 FAQ 使用用户会搜索的原话，不只使用产品术语。

### 6.2 视觉规则

- “无图也能执行”是正文质量底线，不是取消视觉内容的理由。P0、P1、P2 的关键操作与关系说明都必须先预留视觉位，再按优先级补齐素材。
- 截图只回答三类问题：入口在哪里、完成后是什么状态、两个状态有什么差别。
- 一张图只证明一个关键点；紧跟相关步骤；必须有描述性 alt。
- 统一使用虚构的“智能客服知识库升级”演示 Workspace；不得出现真实姓名、路径、API Key 或系统通知。
- 关系图优先使用可版本化、可修改文字的 Mermaid 或 SVG；发布器不支持时再导出 PNG。
- 不使用生成式图片模拟产品 UI。抽象装饰图不进入首发范围。
- P0 视觉位统一登记在 `.authoring/visual-plan-p0.md`。每个视觉位必须写明插入位置、要证明的问题、截图状态、脱敏要求、目标文件名和 alt；尚未拍摄时保留 HTML `VISUAL` 注释，不得在统一编辑时静默删除。
- 图片补齐后必须做一次图文联审：以真实界面为准校正相邻步骤、菜单名和结果描述；删除与图片重复的逐像素说明；必要时调整段落与图片位置。只有图片、alt 和相邻正文一致，视觉状态才能从 `captured` 进入 `verified`。
- P0 预计 15 个截图资产与 5 张示意图；同一截图可被相邻文章复用。界面变化后按受影响文章定向重拍。

### 6.3 技巧规则

快捷键和省步骤技巧就地出现，不单独建立大全。任何技巧都必须在锁定基线的 Mac / Windows 实际界面或自动化测试中验证；仅存在于菜单文案、遗留常量或开发分支的内容不得发布。

## 7. 事实基线与写作流程

### 7.1 锁定文档基线

本轮以 commit `9b359e83e76bf35bee7d46a9a97659af3916f784` 作为可公开产品基线。帮助文档只能描述该基线中真实可见、用户可到达的能力；工作区内未提交的帮助文档不改变产品事实。

事实优先级：

1. 锁定基线运行出的可见 UI 与可重复操作结果；
2. 同一基线的自动化测试；
3. [`CONTEXT.md`](../../CONTEXT.md) 和已接受 ADR；
4. 产品 PRD；
5. 实现代码，仅用于解释已存在的用户行为，不能单独证明功能已发布。

下列事实必须进入写作核对表并记录证据位置与复核日期：数据保存位置、删除或移动语义、Archive、导出内容、跨作用域限制、AI 发送范围、AI 结果确认机制、快捷键和平台差异。

### 7.2 分阶段执行

#### 阶段 A：基线与试写

1. 锁定产品基线，完成高风险事实核对表。
2. 确认栏目和 slug；已发布后不随意改 URL。
3. 试写 4 篇纵向切片：首页、10 分钟上手、QuickNote、FAQ。
4. 用三项任务走查试稿：第一次完成闭环、判断 Record/Todo、找到 AI 数据边界。
5. 根据走查结果固定语气、截图尺度和提示块样式。

#### 阶段 B：P0 首发

按完整用户旅程分组写作，而不是按功能随机并行：

1. 进入：Workspace → 作用域 → Project。
2. 留下：QuickNote → Record → 搜索。
3. 推进：Record/Todo 判断 → Todo 归属 → Project File。
4. 信任：AI 边界 → 本地数据 → FAQ → 排障。
5. 最后更新首页和栏目入口，确保所有入口指向已完成文章。

#### 阶段 C：P1 与 P2

- P1 根据首发走查和真实问题补齐编辑、导出、Tag、连接、Todo 推进与 AI 操作。
- P2 在核心操作稳定后写方法与设置，避免方法论建立在会变化的操作路径上。
- 每一阶段单独发布；后续阶段不得阻塞前一阶段上线。

同一用户旅程由同一写作上下文完成，以保持案例与步骤连续；不同旅程可以并行。每组完成后由统一编辑者做术语、重复内容、跨链和事实审校。

## 8. 验收与维护

### 8.1 单篇完成标准

- 标题能对应一个真实用户问题，首屏能看见答案或结果。
- 操作路径在锁定基线中可重复，关键事实能追溯到证据。
- 正式领域词与 `CONTEXT.md` 一致，作用域无歧义。
- 一篇只解决一个主要问题；不靠长功能清单伪装完整性。
- 风险、限制和不可逆动作出现在相关步骤附近。
- 无图时正文仍可执行；关键决策点已经存在准确视觉位。正式发布前，所有计划纳入本次发布的图片路径、alt 和界面状态均有效。
- 上一级、下一步和相关方法链接可达，没有孤立文章。
- 不含真实隐私数据、密钥、本机路径或未发布能力。

### 8.2 首发完成标准

- 一位未参与开发的人能仅凭文档完成 P0 的第一次工作闭环。
- 用户能在两次点击内从首页到达 Workspace、Record/Todo、Project File、AI 数据边界和排障答案。
- FAQ 的每个问题首段均能独立回答搜索访问者。
- Markdown 链接、图片、标题层级、术语和禁用承诺扫描全部通过。
- P0 文章没有指向尚未完成的 P1/P2 页面；未完成入口标记为规划内容但不发布空页。

### 8.3 维护触发条件

以下任一变化发生时，定向复核相关文章，而不是全量重写：

- 导航、菜单名称、设置分区或快捷键变化；
- `CONTEXT.md` 或相关 ADR 改变领域含义；
- 保存、移动、删除、Archive、导出或 AI 数据边界变化；
- 截图中的界面区域发生明显变化；
- 同一问题在反馈中重复出现，说明现有标题、入口或答案不够直接。

每篇页尾记录“最后核对版本/日期”（对外是否展示由发布器决定）。首发后优先根据搜索词、无结果搜索和重复问题调整标题与入口，再决定是否新增文章。

## 9. 当前明确边界

- `Activity` 与 `Conclusion` 不作为当前用户对象或页面写入。
- Ask、Daily Brief、Project Brief 与其他没有可见入口的 AI Artifact 不写成现有能力。
- 当前进入 Workspace 后没有独立“切换 Workspace”入口，不编造切换流程。
- Record Export 只说明单条 Record 的可携带副本，不描述成 Workspace Backup。
- 不在锁定公开基线中的开发中能力不得加入帮助中心；已经进入基线的应用更新按 P1 文章处理，不阻塞 P0 首发。
- Project Mind 的 Internal Reference 必须服从 `CONTEXT.md` 中的作用域规则，不因示例方便而制造跨 Project 引用。
