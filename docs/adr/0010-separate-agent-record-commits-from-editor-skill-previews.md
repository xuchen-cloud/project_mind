# Separate authorized Agent Record commits from pending Editor Skill previews

[ADR-0003](0003-persist-only-committed-editor-content.md) continues to govern AI Editor Skill previews: an unaccepted AI Modification or AI Answer is not Committed Content and cannot enter persistence, a Record Version, a patch baseline, or model context. Independent Agent Record operations use the authority of a user-enabled scope and the Run's frozen Scope Grant and execution mode. They do not accept, discard, or serialize a pending Editor Skill preview. This makes the distinction required by [E10](../requirements/ai-work-context-engineering-spec.md#e10) explicit without changing the Editor Skill acceptance rule.

The built-in Agent stages Record creation or a patch against canonical block identities. Staging and GUI candidate editing validate Markdown or patch output through the existing canonical document worker and check source ownership, revisions, and authorized references; they do not mutate business content. Collaborate stages and then commits the authorized Record operation without an extra per-operation approval. Review keeps the candidate separate until the user confirms its current output revision through the GUI button or a later natural-language reply interpreted by the model in the same Pi session. In the latter path, the model invokes a decision tool bound by the Host to the pending candidate and that later real user message; both paths use the same durable decision and native commit. A model proposal cannot approve itself, a question does not discard the pending candidate, and a modification invalidates the old candidate before reconfirmation. Read-only rejects these writes. Neither tool arguments nor source text can mint user authority or widen the frozen Run grant.

Record commits reuse the native Record service, canonical document validation, block hashes, revision CAS, immutable versions, and editor coordination. A patch first flushes the target Record's Committed Content and obtains its submission lock; pending Editor Skill review or busy editors return an explicit error. The service checks the current Workspace generation and target again after asynchronous conversion or editor work. A candidate cannot overwrite a newer head or silently retarget another Record.

The native Record transaction atomically binds the saved object and versions, the actual Operation Receipt with its before/after baseline and source context, the output's committed state, and the durable change log. A prepared or staged output is not proof of a saved Record. Successful retries return the original native result and exact operation; they do not allocate a second Record or rebuild a committed candidate with fresh block identities. CommittedChanges notifications are published after storage locks are released and remain hints backed by that log, as established in [ADR-0009](0009-bind-agent-operations-to-workspace-and-atomic-receipts.md).

Undoing a Record modification restores its trusted before snapshot as a new native version. Undoing creation withdraws that Record from normal lists, search, counts, and ordinary reference access while retaining its identity, contents, immutable versions, assets, and reference edges. Restoring a withdrawn creation restores visibility for the same object and checks the withdrawal revision. Recovery uses the persisted receipt baseline; later body or metadata changes, an unresolved editor submission, or new incoming references that would be invalidated by withdrawal produce a conflict and preserve subsequent work. An unavailable historical snapshot or insufficient scope also fails explicitly rather than substituting current content or expanding authority. Deleting the chat does not delete a committed operation receipt.

At the time this decision was first implemented, Record creation, patch, operation history, undo, withdrawal, and restoration were complete, while Todo and File output operations remained planned.

As of 2026-10-09, Todo and File output operations and task-level undo within the same Run are implemented. That undo locates the version before the task began and restores it as a new version; see the [same-Run operation planner](../../src-tauri/src/db/agent_operation_batches.rs), [undo service](../../src-tauri/src/agent/output_service.rs), [Todo recovery](../../src-tauri/src/db/agent_todo_undo.rs), and [File recovery](../../src-tauri/src/agent/file_undo.rs). Cross-Run batch undo is not a current authorization goal. This status does not declare all M1 behavior or target-platform installation acceptance complete; delivery and verification continue under [the existing R05–R13 plan](../requirements/ai-work-context-delivery.md#r05-record-成果与操作记录--104113116).

The same-day user decision extends Review confirmation to the bound model-tool path described above; it does not change Collaborate or Editor Skill preview rules. The model-tool path was implemented in `26fa27a` under [WP2](../requirements/ai-work-context-delivery.md#confirmed-work-packages-20261009): natural-language replies enter the Pi session, and the model invokes the decision tool bound to the pending candidate and later user message. Local targeted validation passed; real Provider and target-platform acceptance remain separate.

## 2026-10-10 target clarification: explicit memory requests

The [unified AI specification](../requirements/ai-work-context-spec.md) adds a distinct, not-yet-implemented memory path: an unambiguous real user request to remember, correct, replace or forget a specified item, or an explicit decision bound to a typed Overview increment, supplies the particular authorization without another confirmation. Read-only still rejects writes, and the native service checks target, request, source and version. This exception does not authorize ordinary Record/Todo/File outputs, allow a proposal to approve itself, or change the later-user-message Review rule above.

## 2026-10-23 implementation status

Explicit memory requests now use native fact identities, immutable revisions and atomic receipts through DSH memory tools. The host captures the real user message and Session ownership; tools cannot supply a confirmation flag or widen the current Project. Default organization may silently change semantics, but creates inferred versions and a 24-hour rollback unit; it cannot inherit an earlier version's user confirmation. Record/Todo/File output approval rules remain unchanged. The typed Overview increment and joint publication work are not declared complete by this status. See the [current memory lifecycle](../requirements/workspace-memory-lifecycle.md).
