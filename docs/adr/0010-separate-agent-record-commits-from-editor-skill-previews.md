# Separate authorized Agent Record commits from pending Editor Skill previews

[ADR-0003](0003-persist-only-committed-editor-content.md) continues to govern AI Editor Skill previews: an unaccepted AI Modification or AI Answer is not Committed Content and cannot enter persistence, a Record Version, a patch baseline, or model context. Independent Agent Record operations use the authority of a user-enabled scope and the Run's frozen Scope Grant and execution mode. They do not accept, discard, or serialize a pending Editor Skill preview. This makes the distinction required by [E10](../requirements/ai-work-context-engineering-spec.md#e10) explicit without changing the Editor Skill acceptance rule.

The built-in Agent stages Record creation or a patch against canonical block identities. Staging and GUI candidate editing validate Markdown or patch output through the existing canonical document worker and check source ownership, revisions, and authorized references; they do not mutate business content. Collaborate stages and then commits the authorized Record operation without an extra per-operation approval. Review keeps the candidate separate until the GUI explicitly confirms its current output revision. Read-only rejects these writes. Neither tool arguments nor source text can mint GUI authority or widen the frozen Run grant.

Record commits reuse the native Record service, canonical document validation, block hashes, revision CAS, immutable versions, and editor coordination. A patch first flushes the target Record's Committed Content and obtains its submission lock; pending Editor Skill review or busy editors return an explicit error. The service checks the current Workspace generation and target again after asynchronous conversion or editor work. A candidate cannot overwrite a newer head or silently retarget another Record.

The native Record transaction atomically binds the saved object and versions, the actual Operation Receipt with its before/after baseline and source context, the output's committed state, and the durable change log. A prepared or staged output is not proof of a saved Record. Successful retries return the original native result and exact operation; they do not allocate a second Record or rebuild a committed candidate with fresh block identities. CommittedChanges notifications are published after storage locks are released and remain hints backed by that log, as established in [ADR-0009](0009-bind-agent-operations-to-workspace-and-atomic-receipts.md).

Undoing a Record modification restores its trusted before snapshot as a new native version. Undoing creation withdraws that Record from normal lists, search, counts, and ordinary reference access while retaining its identity, contents, immutable versions, assets, and reference edges. Restoring a withdrawn creation restores visibility for the same object and checks the withdrawal revision. Recovery uses the persisted receipt baseline; later body or metadata changes, an unresolved editor submission, or new incoming references that would be invalidated by withdrawal produce a conflict and preserve subsequent work. An unavailable historical snapshot or insufficient scope also fails explicitly rather than substituting current content or expanding authority. Deleting the chat does not delete a committed operation receipt.

This decision records the implemented Record creation, patch, operation history, undo, withdrawal, and restoration boundary. Todo and File output operations and cross-Run batch undo remain planned work. It does not declare all M1 behavior or platform installation acceptance complete; delivery and verification continue under [the existing R05–R13 plan](../requirements/ai-work-context-delivery.md#r05-record-成果与操作记录--104113116).
