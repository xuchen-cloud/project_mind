## 1. 目标与使用体验

行为边界（同轮已确认、待实现）：产品中的记忆包含 Overview 与长期记忆等形式，本文“Workspace长期记忆唯一归属”只约束长期条目，不取消 Project Overview。区分任务过程中的记忆行为和回看已有资料及理解的整理行为，两种行为均可更新两类产物；不按“Overview更新/长期记忆更新”拆成两个行为系统。具体沉淀和整理规则由统一 Skill 表达，实际触发、调度和执行由 Harness 承担，复用既有维护与原生能力。

分层补充（2026-10-10，已确认、待实现）：记忆内容与操作属于底层 Context 服务；Harness 的记忆组件调用这些接口组织读取、使用和维护；具体记忆行为确定为一个可编辑的 Skill 文件，工作区统一配置，项目不另设覆盖。用户及具有相应文件修改权限的 Agent 均直接修改并告知实际结果，不增加行为草稿确认流程；下一次模型调用采用新版本，包括当前任务后续调用，已发出的请求正常结束，不重启。本文已有语义提取、整理及使用方式需作为默认行为与必要契约分别审视，不再把所有行为固定在后端。底层继续负责实际目标、来源、版本、原子保存及操作结果。Skill 文件位置、编辑入口和现有固定类别的调整在实施时收敛，旧实现及验证不能证明本分层已接通。

运行设置补充（同轮已确认、待实现）：整理开关、频率、时刻等结构化设置由 Harness 提供调整工具或脚本。Agent 可根据同一请求修改 Skill 和运行设置，两项分别保存，保留成功项，明确告知失败项，重试仅处理失败项；不能仅修改 Skill 中的时间文字便声称调度已改。Skill 修改权限与运行设置修改权限分别核验，无权限或失败时不得假报成功。记忆内容、行为文件和运行设置仍为不同修改目标；文件修改通知与底层记忆操作的既有执行模式分别处理。该部分成功规则不改变第7节的 Overview 与 Memory 联合原子保存要求。

本轮建模补充（2026-10-10，已确认、待实现）：内置 Project Agent 可沿用当前 Workspace 授权可用的长期记忆，例如在项目汇报中使用“日常汇报先说结论”的通用偏好。记忆仍唯一归 Workspace，项目专属背景仍进入 Project Overview。记忆读取与原始资料读取、记忆写入分别表达；沿用记忆不开放其他作用域的原文，也不赋予联合写入能力。外部连接仍须显式获得对应记忆权限；用户纠正、停用、来源失效和撤权须在后续使用中生效。该决定覆盖旧规格中“Project 一律不读取 Workspace 记忆”的目标，现有代码和历史验证不证明新目标已经接通。

长期记忆只有一份逻辑上的权威集合，归属于 Workspace，保存跨任务仍值得使用的背景、方法、领域知识、兴趣、明确偏好和知识入口。Project Overview 保存项目自己的持续理解，包括稳定的项目背景、约束和约定。

用户可以自然地说“记住这个”“以后改成这样”“不要再记住这一条”。由当前会话模型理解意图并调用统一记忆操作，不能在应用侧用关键词、正则或同义词表决定。用户也可通过已有界面查看、纠正、停用和重新启用。系统显示真实结果及必要的范围说明，不要求用户理解每次字段变化。

显式保存补充（2026-10-10，已确认、待实现）：用户在内置 Project 会话里说“记住，以后所有汇报都先说结论”，Agent 将明确的通用偏好保存到当前 Workspace 长期记忆；“本项目汇报按客户模板”保存为 Project Overview 的项目背景与约定。内容和范围明确时，用户请求已经表达这次保存意图，保存成功后简短告知位置，无须为同一记忆重复确认；指代或通用性不明时先澄清。记忆写入绑定真实用户请求及其具体内容，不由普通 Project 范围或记忆读取权限推导，不将来源正文中的要求当作用户指令。模型从请求外自行归纳的信息仍按推断及后台维护规则处理。

一次有相应授权的模型整理，可以同时给出 Project Overview 和 Workspace 记忆的改动，不需要为了决定存放位置再调用一个分类模型。没有值得沉淀的内容时，两边都可以不写。

## 2. 三类内容的边界

| 内容 | 保存位置 | 判断依据 | 示例 |
| --- | --- | --- | --- |
| 项目目标、进度、阻塞、下一步及待解问题 | Project Overview 既有栏目 | 描述这个项目现在的情况 | 本周完成接口验证，预算仍待客户确认 |
| 项目特有且相对稳定的背景、方法、技术约束、决策和约定 | Project Overview 的“项目背景与约定”栏目 | 项目结束后不应自动约束其他任务 | 本项目使用客户模板，部署只允许内网 |
| 跨任务稳定背景、明确通用偏好、可复用方法和领域知识 | Workspace 长期记忆 | 对其他工作仍有价值；不能仅凭一次实践推断通用性 | 我所有日常汇报都先说结论；已验证的通用排查方法 |
| 详细方法、长篇领域资料、完整讨论和历史过程 | 已有 Record、知识节点和会话历史 | 需要保留细节，但不适合常驻上下文 | 一整套排查手册；一场会议的原始讨论 |
| 一次性请求、试探、模型建议 | 当前会话，必要时作为项目的待定信息 | 没有稳定性或明确决定 | 这次试试深色界面，不等于用户一直偏爱深色 |

归属看内容含义，不看它在哪个项目出现。同一来源可以支持两种不同结论，但不能把同一段长文本完整复制两份。模型需要能看到相关的已有条目，才能选择更新或合并；不能只按标题、类别或来源哈希机械地新增。

### 2.1 项目栏目

“项目背景与约定”是 Overview 中可单独读取和更新的栏目，不是独立的 Project Memory 存储或服务。与既有项目定位区分：定位介绍项目是什么；本栏目保留做这个项目时持续适用的规则和背景。

每条保留现有条目身份、来源、修订与有效状态；用户纠正沿既有 Overview 纠正机制执行。项目归档后按既有历史规则保留，不能自动提升为 Workspace 记忆。

### 2.2 Workspace 记忆

沿用背景、领域、兴趣、方法、偏好、知识入口六类；它们是内容分类，不是六份各自无限增长的提示词。复杂领域知识以简短结论或入口留在记忆中，正文留在已有知识层。

“从某项目获得经验”和“记忆属于某项目”是两回事：记忆统一归 Workspace，但来源仍可指向具体项目。归档、排除、删除或权限变化不因跨层沉淀而失去约束；不能通过复制或抽象文字洗掉来源依赖。

## 4. 产生：何时提取，如何判定

### 4.1 触发入口

1. **明确用户请求或决定**：当前会话模型理解“记住/纠正/忘记”或“采用方案B”等真实用户决定、命令，提交范围有限、有类型的增量，可更新 Overview 或长期记忆。不因资料中的引文或工具返回含有这些字样就获取用户授权；普通讨论和方案草稿只登记来源变化。保存文件的收据证明保存完成，不证明方案已被采用。
2. **自动整理**：已启用的既有 Workspace 维护任务处理实际有变化的资料、项目理解或讨论时，同时判断是否形成记忆；没有变化不调用模型。首次建立记忆也沿现有初始化流程。
3. **容量整理**：需要写入但空间不足时，在已有整理任务中合并或提出替换/删除方案。不能产生无限整理循环；无法形成有效操作时保持旧状态并说明需要处理。

自动提取不是每条消息必记，更不意味着每轮聊天后额外调用一次模型。应用关闭后的独立维护仍属于暂缓的 R16。

### 4.2 会话增量与整理协作

- 统一 Skill 按记忆行为、整理行为两节写判断规则。会话即时写入仅处理明确决定、命令及用户点名的新增、纠正、替换或停用；广泛合并、冲突处理、清理和重组进入整理流程。用户可从会话显式请求整理，仍走同一整理入口。
- 会话增量携带实际用户消息或操作收据、目标及预期版本，原生层绑定并核验来源和确认状态；模型不能自报用户确认或重写整个 Overview。沿当前执行模式处理，清晰的明确记忆请求继续遵循不重复确认的既定规则，只读不写入。
- 整理按草稿、校验和原子发布执行，已确认/纠正及停用保护不因统一 Skill 而放宽。Overview 的来源、依赖和版本约束，与长期记忆的类别、用户策略和来源抑制分别保留。
- 会话发布 Project 增量后只标记 Workspace 下游待核对，由整理合并处理；不逐条立即生成上层 Overview。会话增量不声称完成所有来源覆盖，不提前结算整理批次的未消费水位。
- 发布前版本变化时，保留已发布结果、已结算进度及未消费来源，基于最新版本重准备受影响内容并重新校验；旧失效草稿不发布、不覆盖新会话决定，不清空整批积累。仍有效的已读资料只在当前授权和版本复核通过后复用，重复冲突让出并沿既有续跑入口恢复，不无限重试。

### 4.3 判断与可信边界

模型判断稳定性、跨任务价值、重复与矛盾，程序核对结构、目标、版本、来源、授权和预算。无需另起分类模型，也不写业务关键词规则替代模型理解。

新事实与已有记忆相关时，优先判断是补充、替换、合并还是无需变更。一次性提问、助手建议、未完成计划不能变为用户通用偏好。方法可以被记录为有依据的推断，但不能声称用户已经确认其效果。

模型自动产生的条目默认是推断。只有可信用户操作或绑定了真实后续用户消息的明确确认，才能记录“用户确认”；模型不能自己提高确认程度。

## 5. 变化与消亡：统一操作契约

| 操作 | 使用场景 | 保存结果与历史 |
| --- | --- | --- |
| 新增 | 确有新且值得长期使用的内容 | 新条目及实际来源，不重复已有条目 |
| 替换/纠正 | 事实发生变化或用户纠正原判断 | 同一逻辑条目的新版本；旧版本退出有效集合，保留历史 |
| 合并 | 多条重复或互补，可用一条更清楚地表达 | 保留一个明确目标并写新版本；其余条目标记被替代，保留合并关系与完整依据 |
| 整理删除 | 过时、错误、重复或已失去保留价值 | 从当前有效集合和模型检索中移除；保留历史、操作原因和依据，不物理删除原文 |
| 用户遗忘/停用 | 用户明确要求不再使用或记住 | 移出有效集合，持久保存用户决定和抑制；旧版本及旧会话派生内容不能绕过 |
| 重新启用 | 用户明确撤回某条停用决定 | 仅撤回该决定，重新核对当前依据、权限和容量；不恢复其他停用决定或旧 Run 证明 |

“合并”是面向用户的语义操作，可落成一次原子的 replace 加 remove；不必为了这个词另造通用合并框架。

### 5.1 决定权与确认

- 沿用当前会话已选择的执行模式。需要确认时，以一条自然说明概括本次修改，复用现有方案卡和一次任务确认；按钮和模型理解后的回复共用相同执行入口。
- 自动新增符合规则的推断沿已启用维护授权处理。后台模型提出的语义替换、删除和会减少现有信息的合并，参考 Hermes 先暂存为待审方案；不逐项弹窗，也不靠无人回应视为同意。
- 用户已确认或纠正的记忆不能被无人值守整理覆盖。需要改变时提出具体目标和新内容；明确的新用户决定可以替换旧决定，不能把“受保护”做成永远不可更新。
- 权限失效导致的停止提供是读取规则，不需要等待用户确认；也不等同于模型有权永久删除记录。

### 5.2 清理规则

不设置“30 天未使用就删除”等未经用户要求的过期规则。支持时间和使用情况可以帮助判断，不能代替内容是否仍成立。例：“正在准备考试”在明确考试结束后可以被提议移出；不能仅因一个月没有提起而自行判定结束。

清理关注重复、已被新事实替代、已失去作用的临时背景以及过长条目。语义等价的重述不得伪装成新事实；跨来源重复由模型判断、原生核对目标和来源并集，不再以“同类别+同来源”为唯一身份机制。

合并后的来源必须完整保留。混合授权结论不能删掉不方便的引用继续使用；需用当前可见证据重新形成新结论，不能做来源洗白。若合并涉及已有抑制决定，不得让停用内容随目标变化而复生。

### 5.3 遗忘与原文的区别

整理删除允许未来新的有效信息重新形成理解；用户“不要再记住”必须留下持久抑制。系统至少保留用户所见的目标、决定版本及既有来源/类别抑制，并向后续有权的整理过程提供必要的“不再记住”约束。不得把被遗忘正文重新当作正向记忆注入。

当前原生抑制是同 Workspace、同类别、相同原始来源身份，可能覆盖同一来源中的其他同类候选。界面需如实说明；不宣称能从全库删除所有同义转述。不同独立来源的语义重现由模型结合用户约束判断，仍需真实模型负例验证，不能用字符串黑名单冒充理解。

停用、删除、纠正或被替代的旧版本不能被普通记忆搜索或历史 Run 引用重新带回模型。用户主动查看自己的历史仍沿现有 GUI 历史规则；原始 Record/File/会话不随记忆操作删除。

## 6. 使用：精简有效记忆、按需详细读取

### 6.1 会话快照

有 Workspace 记忆读取权限的会话，在首次真实任务开始时装入完整的、当前授权可见且符合预算的精简有效记忆快照。创建空会话不读正文、不调用模型。快照保留条目身份、版本和确认程度；详细依据沿工具按需回读，不把完整来源附加到提示词。

不再以 node ID 顺序取前八条充当“长期记忆”。八条导航仍可用于普通知识入口；长期记忆需要独立明确的内容预算和精简规则。模型上下文中的记忆与其他系统提示分开标明，记忆文字不是可以覆盖工具权限的指令。

同一快照只在会话上下文中保留一份，不把同一内容每轮再追加成新消息。发给 Provider 的请求通常仍包含当前上下文，因此不承诺每轮零记忆 token 成本，也不依赖所有 Provider 都支持提示词缓存。

### 6.2 更新与失效时机

有效记忆变化时，下一次模型请求使用新快照；普通知识版本变化不要求无关记忆重建。用户纠正、遗忘、撤权和删除的过滤必须在下一轮前生效；正在生成的旧请求不能被假称已使用新记忆，后续写入仍校验最新版本。

继续会话、恢复旧会话和 Pi 压缩后重建上下文，都要复核记忆版本与最新用户策略，不能只刷新新快照而留下旧消息中的失效派生内容。复用现有 Run 来源账本和原生 Pi 会话边界，不另建会话存储。

### 6.3 容量

长期记忆只保存精简事实及知识入口；长方法、教材和大段背景转为已有知识的入口，不自动复制成新 Record。容量计算包含实际记忆文本及封装开销，与系统提示、会话和输出预留合并核对模型可用输入。

需要一个用户可见、可解释的记忆预算设置；其有效值不得超过所选模型扣除必要预留后的能力。**本需求不冻结新的任意字符常量或百分比。** LM4 工作包需在小/大模型的真实序列化输入上确定并记录可解释默认值、单位和边界；提交默认值及验证依据后才算该包完成，不能把这一参数留到产品发布后。Hermes 的固定字符数只作为参考，不直接成为产品限制。

超额时先通过明确操作精简；有待确认的整理时保留原有效集合，新内容保持待处理，不假报已记住。切换到更小模型而旧集合放不下时，不任意截断、不再次增加调用次数配额；本轮改为按需记忆检索并明确报告尚未装入完整快照，按实际剩余预算返回结果，不能仍宣称全量记忆已注入。整理完成后再恢复完整精简快照。

长会话的 Pi 压缩和长期记忆精简是两回事，各自受模型输入能力约束。禁止用反复扩大预算或不断丢弃旧内容来掩盖整理失败。

## 7. 一次整理同时更新两处

### 7.1 输入与输出

联合整理读取本批真实变化、相关 Project Overview、授权可见的 Workspace 记忆和用户纠正/遗忘约束。只读当前批次所需内容，不扫描所有项目原文。项目归属和跨任务价值由同一次模型生成判断。

生成结果包含两个明确部分：项目概览操作，以及 Workspace 记忆操作。各自可为空；每个操作携带目标与已读取证据索引，原生端绑定真实 ID、修订和来源，不接受模型自报权限、用户确认或成功结果。

“一次”指不为两种沉淀重复生成/分类，不是保证任何任务连工具读取、失败重试在内都只发生一次 Provider 请求。已有保存草稿恢复不再次生成；确需恢复失败时沿既有机制执行，不热循环。

### 7.2 授权与原子保存

联合保存由具有 Project 和 Workspace 对应授权的既有维护服务执行。默认 workspace 范围可以使用获准来源；内置 Project Agent 可获得单独的 Workspace 记忆读取能力，未获该能力的会话或外部连接不能读取。记忆读取不授予记忆写入或联合保存权限；本次不静默扩展旧外部 grant，也不让只读连接获得记忆写权限。

未获 Workspace 记忆写入授权的请求只能保存项目部分。内置 Project 会话中的明确通用记忆保存请求可获得绑定该次操作的 Workspace 记忆写入授权，无须用户切换会话；外部连接和无人值守整理仍沿各自授权判断。一次明确请求需要同时保存两处时，沿联合保存契约核对两个目标；单项保存不得声称已完成双写。

一项被批准的联合批次在同一 Workspace 数据库内核对两个目标的基线、记忆策略版本与来源，再在同一事务中保存概览、记忆操作、批次结果和处理进度。任一目标冲突或越权则该次联合保存不部分成功；保留草稿及未消费进度。待审方案期间不提前推进该批已完成水位，其他无依赖任务继续按既有队列处理。

使用既有批次身份、幂等和版本检查；不新建跨库分布式事务、另一套任务系统或重复日志权威。同一批重放不生成第二份条目。确认后目标变化需重新核对并展示变化，不能按旧批准覆盖新版本。

## 8. 存储与初始化边界

整个 AI 功能尚未开始用户测试，本轮直接按新模型实现，不承担旧 AI 数据迁入、旧格式兼容或历史身份映射；不为开发阶段的 Project Memory 增加转换流程。此范围决定覆盖旧计划中相关 AI 迁移要求。

1. 复用已有知识正文、不可变版本、来源关系和用户策略实现，活动 Memory 唯一归 Workspace，原生写边界拒绝 Project Memory。
2. Project 稳定信息进入 Overview 的“项目背景与约定”栏目；长资料保留在知识正文中，栏目提供简短说明和入口。
3. 按新结构创建、保存和重开后，记忆归属、项目栏目、版本及用户决定保持一致。后续产生的纠正、遗忘和版本记录仍按本需求保存。
4. 不改动项目原有 Record、File、Todo、QuickNote 等业务资料；不以简化 AI 结构为由清空业务数据库。

具体表与 DTO 在现有结构上最小修改；不增加旧 AI 转换器、兼容层或通用迁移框架。

## 9. 用户可见交互

- Project 知识面板展示“项目背景与约定”，不再提供独立“项目长期记忆”管理区。
- Workspace 记忆面板展示当前有效条目、依据、推断/用户确认，以及待处理的整理建议；用户可查看修改和退出有效集合的原因。
- 会话内用简短业务语言说明目标与动作，例如“把‘喜欢详细汇报’改成‘日常简短、专题详细’，是否确认？”；不展示一串数据库操作作为默认方案说明。
- 合并和遗忘说明实际范围；用户只需对同一任务确认一次。失败、冲突、预算不足和等待确认如实显示，不把待审候选显示为已生效。
- 容量说明区分“当前保存了什么”“本轮实际带入了什么”“需要时还能搜索什么”。
