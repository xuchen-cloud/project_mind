## 1. 要解决的问题

项目的信息分散在 Record、Voice Record、File、Todo 和会话里。助手需要理解它们之间的关系，也需要知道哪些判断已经改变。用户不应该在每次提问前重新介绍项目，助手也不能每次把全部材料和历史对话读一遍。

这次建设三种相互配合的能力：

1. **持续形成知识**：AI维护Project Overview、关联知识和会话摘要；Workspace进一步承载跨项目理解与长期记忆。
2. **按问题逐步读取**：先获取最小知识入口，再决定读哪些摘要、原文片段或完整文件。
3. **直接完成工作**：通过内置助手或外部Agent创建、修改Record/Todo/File，保存版本、引用和操作记录，并允许撤销。

Project首页不增加“继续工作”卡片，也不把项目概览做成必须阅读的首页模块。Overview首先服务于助手；用户需要核对、纠正或查看来源时，再从助手内打开。

## 2. 概念和边界

### 2.1 Overview与QuickNote必须独立

| 概念 | 作用 | 谁维护 | 如何使用 |
| --- | --- | --- | --- |
| QuickNote | 用户随手记录的临时想法和待整理内容 | 用户通过现有编辑流程维护 | 可作为临时来源；用户决定是否转为Record或Todo |
| Project Overview | 项目目标、进展、关键知识和行动的派生理解及导航 | AI定期更新，用户可纠正 | 助手按问题读取其中相关部分 |
| Workspace Overview | 跨项目工作和Workspace直属长期知识的更高层理解 | AI基于下层变化更新，用户可纠正 | Workspace范围提问的知识入口 |
| 关联知识页 | 对一个主题、决定或比较的跨来源综合理解 | AI维护并保留证据 | 从Overview或检索结果继续展开 |
| 会话摘要 | 一段讨论的问题、理由、决定、成果和未决事项 | AI分段整理 | 定位历史讨论及其原始消息 |

**Overview不能复用QuickNote的字段、正文、保存接口或编辑状态。** 生成、重建、恢复Overview都不能覆盖或清空QuickNote。QuickNote中的“考虑做某事”仍然是临时想法，不能被概览自动标成用户已决定的目标。

当前代码的对外字段已为`quickNote*`；内部`summary*`历史字段仍表示QuickNote。后续Overview使用独立表和服务，不改变这些旧字段的语义。具体代码边界与兼容要求见[工程契约E1](https://github.com/xuchen-cloud/project_mind/blob/codex/ai-enhancement/docs/requirements/ai-work-context-engineering-spec.md#e1)。

### 2.2 原始内容与派生知识

Record、File Version、Todo、Voice Transcript和原始消息提供依据；Overview、知识页、资料摘要和会话摘要负责组织、压缩与连接这些依据。

派生内容必须保留来源及对应版本。摘要之间相互引用不能凭空增加证据，AI建议不能因为被总结多次就变成用户确认的事实。原始材料仍可按用户任务版本化修改；原始Transcript保持现有只读规则。

这些派生知识不必全部转成普通Record。只有需要独立查找、引用或作为正式成果保留时，才创建或更新Record，避免项目被自动总结填满。

### 2.3 作用域

- Project助手只读取同Project内的内容和会话，不自动读取Workspace个人记忆或其他项目。
- Workspace助手可以在授权范围内结合各Project的知识，以及Workspace直属Record、Todo和会话。
- File继续属于Project，本次不增加Workspace File，也不自动建立收集箱项目。
- 排除来源、删除会话或缩小权限后，其派生知识也要及时失效，不能通过旧摘要继续泄露。

## 3. 知识如何建立和持续更新

### 3.1 Project Overview包含什么

每个Project维护一份Overview，内部区分相对稳定的背景与持续变化的状态。

| 内容 | 示例 | 来源 |
| --- | --- | --- |
| 目标、背景、约束 | 解决什么问题，本阶段做与不做什么 | 目标Record、方案、用户明确表达 |
| 进展与重要决定 | 已推进到哪一步，为什么作出某个取舍 | Record、会话、Voice Record、实际操作 |
| 关键知识入口 | 某个问题应看哪份材料、哪段讨论 | 关联知识页、资料/会话摘要和原文引用 |
| 行动与阻塞 | 下一步、当前Todo、需要重新评估的事项 | 实际Todo状态及相关证据 |
| 未决与冲突 | 哪些问题尚未定论，哪些资料意见不同 | 双方来源和发生时间 |

“很久没更新的Todo可能不再重要”只能作为有依据的待复核判断。知识维护不能仅凭时间久就把原Todo完成、删除或降级。

### 3.2 首次建立与定期维护

启用助手时，说明资料发送范围、模型和维护策略；启用后自动分批建立知识，不要求用户逐个配置主题。大项目先形成部分覆盖的入口，再按预算补齐；期间仍可检索和提问。

正常使用时，内容变更先登记到待处理集合，不立即调用模型重新整理。默认每日本地时间03:00检查，可改为每48小时或其他时间；只处理发生变化的范围。

一次维护按以下顺序进行：

1. 合并同一对象在这段时间里的多次修改，保留删除、恢复和排除信息。
2. 整理新增会话片段及受影响资料，更新相关知识页和摘要。
3. 使用旧Project Overview、这次增量和必要原文，调整受影响条目。
4. 在Workspace阶段，消费变化的Project Overview和Workspace直属内容，更新高层知识。

未变化的项目不调用模型；未受影响的知识不反复改写。失败保留旧版和待处理进度，不把未处理资料标成已覆盖。用户的当前任务优先于后台维护。

首期只有应用运行且Workspace打开时执行；错过夜间时间后，在下次打开时合并补跑一次。应用关闭后的独立运行属于后续批次，不能承诺电脑休眠时仍会更新。

### 3.3 会话成为知识来源

会话本身有知识价值，无需先转成Record。摘要保留讨论问题、方案比较、决定及理由、未决问题、实际成果，并引用原始消息。

长会话采用分段摘要，保留早期讨论的入口。后续推翻决定时，最新知识显示新结论，旧摘要仍能解释当时为什么这样决定；不会在不断压缩一份总摘要时丢掉全部历史。

用户计划、用户确认、AI建议和实际执行结果分别标注。失败或中断任务中的已完成操作可以保留，但不能把未完成回复写成“已完成工作”。

### 3.4 Workspace长期记忆

Workspace既消费项目概览，也消费自身的长期资料。它可承载用户工作背景、领域和兴趣、可复用方法、知识入口及明确偏好。

单次提问或AI建议不能自动升级为长期偏好。用户可以查看、纠正、停用或要求不再记住某一条；停用信息不能在下轮维护时自动复生。项目归档不必抹掉仍有依据的通用经验，但必须保留来源状态和权限边界。

## 4. 助手如何回答一个问题

### 4.1 新会话只从最小入口开始

创建空会话时不预读项目正文，也不发起模型请求。用户发送问题后，助手获取项目定位、少量相关知识入口、更新时间和必要变更提示。完整Overview、全部Todo、历史摘要和个人记忆都不默认附加。

首轮入口默认不超过2000个Unicode字符。完整知识可以很丰富，单次披露必须受控；工具逐次返回量和整轮累计读取量都由服务端限制。

### 4.2 根据问题决定展开到哪一层

| 层级 | 内容 | 用途 |
| --- | --- | --- |
| 最小入口 | 项目定位、相关目录项、知识状态 | 判断去哪里找 |
| 关联知识 | 相关主题、决定、比较与证据链接 | 理解跨资料关系 |
| 资料或会话摘要 | 某份资料/讨论讲了什么，原文在哪里 | 确定要核对哪一部分 |
| 局部原文 | 正文块、消息范围、转写时间段 | 核实事实、措辞、冲突或修改基线 |
| 完整原文 | 明确选中的单个对象，必要时分页 | 全文审阅、整体结构修改或局部不足 |

这些层级可以跳过，也可以提前停止。概括项目方向时可以依据有效摘要；问精确原话时要读对应消息；用户直接指定HTML要求修改时，可以直接读取那个文件。

例如“上次为什么暂缓权限管理”，读取路径可以是：决定入口→相关会话摘要→用户作决定前后的几条消息→回答并附引用。既不用读全部历史会话，也未必需要读完整的一次会话。

### 4.3 新鲜度、来源与停止条件

Overview整理后产生的新变化会作为相关提示供助手发现。已变化的条目标过时；需要当前状态时读取当前对象，不能把旧摘要当今天的完整事实。

如果概览没有这个问题的入口，就检索知识页或原始资料；摘要缺失不阻止直接读原文。未命中不能直接推出“项目里从未讨论过”。

问题所需证据充分时停止读取。只读过摘要就如实说明依据；全文被截断或预算不足时说明覆盖范围，不能声称已经通读。引用点击应定位到对应Record、File Version、Voice时间段或会话消息。

## 5. 助手如何直接完成工作

### 5.1 默认确认后执行，完成后可撤销

新启用或未显式配置执行模式时，默认“确认后执行”（`review`）。助手先在消息流中提出一个与当前用户任务对应的简短业务方案，例如“更新项目计划，并创建3项待办”，用户确认后执行。一个任务涉及多个Record、Todo或File时合并确认一次，不逐对象、逐块或逐次保存弹窗，也不要求检查技术字段。用户可主动选择“自动执行”（`collaborate`）或只读；已有明确选择的自动执行设置保留，不因默认值调整被重置。模式在运行开始时冻结，当前设置变化不能改写旧方案的执行模式。

方案在所属助手轮次中显示“确认执行”“取消”按钮。用户在输入框明确回复确认或取消，走与按钮相同的候选决定和执行路径；指向哪个待定方案不明确时先澄清。用户补充修改方案时，旧方案先失效，助手给出调整后的新方案，再等待新的确认，不能把补充要求当作对旧方案的批准。确认、取消、失效和实际执行结果保留在历史会话中。

纯讨论可以只回答；与任务相关的行动和独立成果在确认后保存，自动执行模式则直接保存。会话中以一次简短业务摘要报告真实结果并提供实际对象入口，详情、差异、来源与撤销按需展开，不额外批量制造总结Record。跨对象逐项调用原生服务，不承诺全局原子性；部分成功、失败或取消显示已完成项和未完成项，不能因回复结束就宣称全部完成。

目标存在歧义、权限不足或发生并发冲突时，需要具体澄清或处理；AI不能静默覆盖后来发生的人工编辑。中断保留已完成操作和真实收据，重试只处理未成功项，不重复创建或重写已提交成果。

### 5.2 各类对象支持的操作

| 对象 | 首期能力 | 可恢复方式 |
| --- | --- | --- |
| Record | 创建，按稳定块修改、追加、删除 | 正文版本、按块差异、恢复为新版本 |
| File | 创建，修改已有文件；保留同一个File ID | 复用现有File Version，恢复产生新版本 |
| Todo | 创建，修改内容、期限、子项及状态 | 修订校验和操作前后快照 |
| 新建成果 | 撤销本次新建 | 可恢复撤回，保留内容和对象ID |

Record正文版本与GUI保存必须使用同一并发规则。File更新复用现有版本服务，不另建AI文件历史。批量撤销逐对象给出结果，不声称跨数据库与文件系统全局原子。

QuickNote不属于这份Agent正文修改接口；原始Transcript、声音轨和只读纪要也不开放修改。现有编辑器AI待接受预览继续遵循Committed Content规则。

### 5.3 HTML交互稿是首期主要File场景

用户说“根据需求生成一个可点击HTML”，助手读取相关资料，提出方案，经本次任务确认后创建Project File并提供预览；用户已选择自动执行时直接创建。用户再说“把筛选改为多选”，助手读取同一File的当前源码，修改后生成新版本，不另建一个同名文件。

预览在非模态主工作区域打开，现有会话保留侧栏；窄屏在两者间切换，可一边查看稿件一边继续讨论同一File。提供只读源码/预览切换、响应式宽度、继续修改和版本入口，复用已有固定版本源码读取与历史恢复。历史预览固定在所选版本；恢复旧稿核对实际当前版本/hash并创建新版本，内容变化时明确要求重载，不静默覆盖。流式生成期间不反复重载预览，只加载完整、已提交内容。

首期完整支持内联CSS/JS的单文件交互稿。已有HTML也可修改和保存；依赖外部CDN、相对资源或后端时，显示未加载依赖，不承诺完整Web工程构建。可执行HTML在隔离环境预览，不获得应用文件、凭据或内部命令能力。

R08先通过实际fixture确定隔离实现，不在规格中预先认定某种surface已验证。组件fixture、真实文件IPC、真实模型任务及macOS/Windows平台隔离分别验收，不能以模拟预览通过宣称整项完成。

## 6. 用户界面与设置

Project标题区提供“助手”入口；Record/File菜单可“带入助手”或修改当前对象。助手是稳定的非模态右侧面板，打开后仍可操作业务页面，也可展开到主工作区域；同一会话在面板切换、收起和展开间保留输入草稿和阅读位置。窄屏使用单栏并保留返回业务页面的入口，不用带遮罩的审阅Dialog承载日常对话。布局、滚动和动效复用现有设计规范，不固定新的像素规则。

顶部只保留项目/会话标题、历史、新会话和更多菜单。历史会话按需展开，空态保留“问项目资料”“制作内容”两个入口，也可直接输入问题。输入框始终是主操作入口；模型配置、工具调用验证和知识维护进入设置或更多菜单，不在会话主轴常驻技术信息。打开面板本身不会预读完整项目知识。

消息按用户任务轮次组织。用户消息用浅底背景，助手正文正常排版Markdown；工具过程在所属轮次折叠、低强调，常态只显示业务活动摘要，错误不能随过程折叠而消失。方案确认与真实结果紧跟对应助手轮次，不把历史操作集中排在会话末尾，也不重复显示同一个收据结果。详情、来源和差异按需展开；用户向上阅读时不抢滚动位置，在底部时跟随新增正文及异步方案/结果。

会话展示复用官方Pi展示组件并作薄适配，保持上述交互与现有设计规范；模型调用、会话保存和权限继续使用Mind已有链路。具体复用边界见[工程契约E14](https://github.com/xuchen-cloud/project_mind/blob/codex/ai-enhancement/docs/requirements/ai-work-context-engineering-spec.md#e14)。

运行中可以继续写草稿，但同一会话不并发发送。首版采用停止后再发送：用户明确停止当前运行，等待已开始操作结算，再发送保留的草稿；不隐式入队、不做自动续发或steering框架。关闭面板不等于取消运行。

已保存成果链接到现有Record、Todo或File页面，用户可在那里继续编辑，也可在查看成果时继续与助手对话。当前讨论对象用可移除的来源/目标提示明确显示；“继续修改”绑定实际对象ID和当前版本，移除提示不删除对象，也不静默切换scope。HTML隔离预览由R08交付，不在GUI收口包另造编辑器或提前开放未隔离的执行页面。

“项目知识”放在助手菜单内，按需查看整理时间、覆盖情况、来源、纠正/排除和刷新入口；不在首页增加“继续工作”卡片。用户不需要先理解Overview、MCP或Pi才能提问。

设置复用现有AI Profile，只增加项目助手和外部连接相关选项：启用范围、模型覆盖、维护频率、执行模式、连接权限。没有兼容模型、资料未处理或维护失败时，说明真实状态；普通笔记、Todo和文件功能照常可用。

界面借鉴官方源码中的会话组织方式：[OpenCode的会话内权限提示](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/pages/session/composer/session-permission-dock.tsx)、[DeepSeek Harness Chat](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-chat/README.md)的消息分组、过程折叠和滚动状态，以及[其ApprovalPanel](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-approval/src/client/ApprovalPanel.tsx)的原位决定。[Hermes Web ChatPage](https://github.com/NousResearch/hermes-agent/blob/main/web/src/pages/ChatPage.tsx)实际嵌入终端，并配有结构化事件侧栏，仅参考会话/过程组织，不将其当作完整聊天GUI模板。Mind的同任务一次确认、业务对象导航、scope、版本和收据规则由本规格定义，不照搬这些项目的工具权限或队列系统。

## 7. 内置Agent与外部接入

内置助手优先使用Pi SDK和应用自带Node sidecar。Pi负责会话与工具执行，Mind负责领域语义、数据、权限、版本、预算和恢复。

CLI、MCP与内置助手调用同一业务服务，获得相同范围内的知识与写入能力。读取默认小结果，支持目录、摘要、局部原文和分页；修改使用明确对象ID、预期版本和幂等请求ID。CLI支持结构化结果和schema发现，MCP首期使用本机stdio。

外部连接一次配置作用域和能力，默认推荐单Project协作预设，可改为只读或自定义。会话历史读取需要session.read；模型维护刷新另有权限，普通读取不隐式产生模型费用。

后续再接入Pi CLI、Claude Code等外部运行时，以及可配置任务菜单。各CLI需单独能力探测，不能假定相同协议，也不能把工作目录当成操作系统隔离。应用关闭后的独立WorkspaceHost单独交付。
