## 1. 产品背景与四大拍板决策

### 1.1 核心痛点与产品价值
用户在长期使用 AI 助手推进多项目工作时，面临三大核心痛点：
1. **重复交代背景**：每次新开会话都要重新解释个人汇报风格、编码规范或角色背景。
2. **多项目上下文串台**：在服务不同客户或项目时，A 项目的专属周报模板或技术决议容易被误用到 B 项目。
3. **改不准、忘不掉、打扰多**：口头说“改掉/忘掉”后模型依然按旧习惯输出；或者后台整理频繁弹窗要求审批，造成使用负担。

**产品成功判据**：
* 用户明确说“记住”后真实落库保存，无需繁琐二次弹窗确认。
* 该用时按任务精准召回，不该用时跨项目严格隔离。
* 用户纠正或要求遗忘后，**当前任务的下一次模型请求立即采用新决定**。
* 后台自动整理默认静默生效不打扰，且支持 **24 小时内按原子操作单元一键回退**（单条 patch 独立，merge 整组恢复）。

## 2. 记忆分类归属与三级加载架构

### 2.1 记忆归属边界（存哪儿？）
系统严格区分**跨项目通用信息**与**项目内专属信息**，从存储源头杜绝跨项目串台：

| 信息类型 | 归属位置 | 典型示例 | 存储与调用规则 |
| :--- | :--- | :--- | :--- |
| **通用稳定事实与偏好** | `Workspace 长期记忆` | “以后日常汇报先给结论，再列风险与下一步。” | 跨项目通用；保留 6 大分类标签（背景、领域、兴趣、方法、偏好、知识入口）；支持绑定**适用场景条件**。 |
| **项目专属背景与约定** | `Project Overview` | “客户甲的周报必须使用合同附件 B 模板。” | **严格锁定在当前项目内**，绝不因出现频次高而自动升级为全局 Workspace 偏好。 |
| **项目阶段进展与决议** | `Project Overview 决议栏` | “10 月评审决定采用方案 B；交付日调整为周五。” | 记录生效时间与新旧替代关系，区分“历史曾用方案”与“当前生效决议”。 |
| **长篇流程与完整方法** | `知识库 / Record / File / Skill` | “过去三次客户验收的 12 步完整核对清单。” | 长期记忆仅保存**一句简短原则 + 资料入口链接**；完整长文在需要时按 L3 依据层读取。 |
| **记忆行为与整理周期** | `统一记忆行为配置 + 运行设置` | “只记我明确要求的信息”、“每周日晚上整理”。 | 行为规则文本与真实定时调度设置分别独立保存，不混入业务记忆正文。 |
| **一次性要求与临时试探** | `仅当前会话上下文` | “今天这篇文案试试更活泼的风格。” | 仅在当次回复中生效，**严禁后台自动提取为长期偏好或正式决议**。 |

### 2.2 每次对话的三级上下文加载架构（怎么用？）
以下为目标分层策略；真实 50～100 中文多轮三组对照 gate 通过前，每次请求默认使用预算内精简 `snapshot`，不宣称已按 L1/L2 默认检索。L3 原文始终按需回读：

1. **Layer 1 · 核心常驻层 (Core Memory)**
   * **内容范围**：用户已明确确认、无特殊场景限制的高频全局背景与核心个人偏好。
   * **加载策略**：分配独立的小额 Token 预算，在每次会话请求中默认常驻；用户在管理台可手动置顶或移出核心层。
2. **Layer 2 · 按需检索层 (Task-Retrieved Memory)**
   * **内容范围**：带有特定适用场景条件（如“技术方案分析”、“代码评审”）的 Workspace 记忆 + 当前所在项目的 `Project Overview` 约定与最新决议。
   * **加载策略**：根据当前用户输入意图、任务分类及所属项目 ID 动态检索匹配项；不匹配当前任务场景（例如写技术推导时遇到“日常汇报要极简”的规则）或其他项目的专属记忆一律过滤。
3. **Layer 3 · 依据回读层 (Evidence Lookup)**
   * **内容范围**：原始对话锚点上下文、Record / File 原文段落、真实工具执行结果记录。
   * **加载策略**：默认不塞入常驻上下文；仅当用户追问“当时原话是怎么说的”或需要核对完整流程文档时按需调用。**若源文件已被用户删除，L3 原文不可回读，但已提炼进入 L1/L2 的历史结论继续正常生效。**

### 2.3 核心数据模型属性要求
每条长期记忆在底层 SQLite 中需维护以下核心业务字段（无需向普通用户暴露底层数据库 ID）：
* **事实唯一身份 (`fact_id`)**：同一偏好在新对话中被再次提及或补充时，更新原条目并追加证据，不重复创建新 ID；一段话包含两个独立偏好时拆分为两条独立记录。
* **归属与分类 (`scope` & `category`)**：`Workspace`（背景/领域/兴趣/方法/偏好/知识入口）或 `Project (<project_id>)`。
* **适用场景条件 (`condition_scope`)**：可选字段，仅在存在明确边界时记录（如 `日常项目汇报`、`技术方案分析`），无条件则全局适用。
* **时效区间与替代链 (`valid_from`, `valid_to`, `superseded_by`)**：支持记录事实的生效期及被哪条新记忆替代，确保回答现状问题时使用最新有效事实。
* **来源与原文状态 (`source_refs`, `source_status`)**：关联真实消息或文件引用；当源文件被删除时，该来源引用的状态标记为 `source_removed`（原文已移除），**但不改变记忆本身的 `active`（有效）状态**。
* **不可变版本与回退操作 (`revision`, `rollback_id`, `auto_organized_at`)**：每次整理保留完整前后版本与操作单元。连续整理不能覆盖较早快照；合并回退原子恢复其成员与替代关系，其他独立操作不变。

## 3. 核心用户故事与验收标准 (User Stories & AC)

### US-01 [P0] 自然语言明确记住通用偏好
* **用户故事**：**作为**高频使用助手的专业用户，**我希望**在对话中直接说“记住以后日常汇报先给结论”时，系统直接写入全局 Workspace 记忆并给出明确回执，**以便**无需繁琐的二次确认弹窗，且从下一次模型请求起就能自动按该习惯输出。
* **验收标准 (Acceptance Criteria)**：
  1. **Given** 用户在对话中发出指代明确、内容清楚的“记住…”指令；
  2. **When** 系统完成权限校验并实际写入 SQLite 成功后；
  3. **Then** 助手直接回复“已保存到 Workspace 记忆：[内容摘要]。下次模型请求起使用”，不弹出二次确认；
  4. **Then** 若底层数据库写入失败，必须如实告知“本次未保存成功，现有记忆未变”，严禁在未落库时虚假回复“我记住了”。

### US-02 [P0] 项目专属约定严格隔离 (Project Overview)
* **用户故事**：**作为**同时负责多个客户项目的项目经理，**我希望**在项目甲里要求记住的“周报使用客户甲合同附件模板”只保存在项目甲的 `Project Overview` 中，**以便**切换到项目乙写周报时，绝不会串台套用客户甲的模板。
* **验收标准 (Acceptance Criteria)**：
  1. **Given** 用户在【项目甲】会话中声明项目背景、客户模板或阶段决议；
  2. **When** 系统保存该信息后，用户切换到【项目乙】发起同类周报撰写任务；
  3. **Then** 该条约定仅存在于【项目甲】的 Overview 中，【项目乙】的任务检索召回率为 `0%`。

### US-03 [P0] 局部精准纠正与场景条件限定 (Patch 机制)
* **用户故事**：**作为**需要对既有习惯做细化修正的用户，**我希望**说“日常汇报才极简，技术方案分析要完整推导”时，系统只局部更新目标记忆并加上适用条件，**以便**不会把同一条或其它已存偏好顺手覆盖丢失，且不同任务能匹配正确的输出风格。
* **验收标准 (Acceptance Criteria)**：
  1. **Given** 记忆库中已存在“回答尽量简短”的旧偏好及其他无关偏好；
  2. **When** 用户发出纠正指令“刚才记得太笼统了，日常汇报简洁就好，技术方案分析要完整解释推导”；
  3. **Then** 系统通过局部 `Patch` 将原记忆限定为 `[适用场景: 日常汇报]`，同时独立新增一条 `[适用场景: 技术方案分析] 需完整展开推导过程` 的有效记忆，其余记忆条目保持原样；
  4. **Then** 在当前会话紧接着的下一次模型请求中，立即按更新后的场景条件生效。

### US-04 [P0] 主动遗忘与防复生抑制
* **用户故事**：**作为**希望彻底清除某条过时偏好的用户，**我希望**说“不要再记住我喜欢极简回答”或在管理台点击“主动遗忘”后，系统立即停止使用并永久抑制该结论从历史聊天中被重新提取，**以便**不用删除原始聊天记录，也能确保旧习惯不会在后台整理时死灰复燃。
* **验收标准 (Acceptance Criteria)**：
  1. **Given** 用户明确要求“忘掉”某条有效记忆；
  2. **When** 操作提交成功，且后续触发新一轮对话或后台自动整理任务时；
  3. **Then** 该条记忆立即从 L1/L2 有效上下文中剔除，并生成持久化的**防复生抑制记录**；
  4. **Then** 原始历史聊天记录、Record 与 File 保持完整不删除，但后台提取器不会再从旧原文中重新提炼出该条已遗忘的偏好。

### US-05 [P0] ★ 原始文件删除后保留历史结论有效（本次拍板新规则）
* **用户故事**：**作为**定期清理或归档本地文档的用户，**我希望**当我删除了曾经引用过的会议纪要或外部文档时，之前已经从该文档中提炼出的历史记忆结论依然保留并有效，**以便**清理源文件不会导致助手突然“失忆”，只有当我用新记忆覆盖或主动遗忘时才替换它。
* **验收标准 (Acceptance Criteria)**：
  1. **Given** 某条有效记忆（如“核心账务表禁止使用外键级联删除”）提炼自文档《Q3架构评审纪要.docx》，随后用户将该文档删除或归档；
  2. **When** 用户在后续对话中发起数据库设计相关提问，或在管理台查看该条记忆时；
  3. **Then** 该条记忆的状态**继续保持【有效 (Active)】**，正常进入 L1/L2 上下文参与回答；
  4. **Then** 来源实际删除后，“查看依据”标记“源文件已移除（不可回读原文段落），历史结论继续有效”；仅归档时按真实可用性和授权显示，不能一律标记原文已移除；
  5. **Then** 来源删除不影响结论；新规则覆盖、主动遗忘/停用或已明确的有效期结束，才会使其退出当前采用集合，历史仍保留。

### US-06 [P1] ★ 后台默认静默整理 + 24 小时按操作单元一键回退（本次拍板新规则）
* **用户故事**：**作为**不想被频繁审批弹窗打扰但需要纠错兜底的用户，**我希望**后台自动合并重复记忆或精简归纳时默认直接静默生效，并在整理后 24 小时内允许我从具体条目进入对应原子操作单元的一键回退，**以便**平时享受零打扰体验，万一发现某条自动整理不准确也能精准撤销该次操作；单条 patch 独立，merge 整组恢复。
* **验收标准 (Acceptance Criteria)**：
  1. **Given** 系统默认将“后台整理需我先审批”开关设为【关闭（默认静默模式）】；
  2. **When** 后台维护任务完成重复记忆合并或内容更新时；
  3. **Then** 新版本直接静默切换为【有效】状态，无需用户事前确认，并在管理台“最近 24h 自动整理”分类下高亮标记该条目；
  4. **Then** 用户在 24 小时内点击任意单条记忆右侧的 **【24h 一键回退至整理前】** 按钮后，对目标操作全部成员核验当前版本后，原子恢复整理前文本、条件、来源和替代关系，并锁定防止再次自动整理；同批其他独立操作不受影响。后续人工编辑、遗忘或其他版本变更使旧回退产生明确冲突，不能覆盖后来的用户决定。

### US-07 [P1] ★ 后台整理人工审批模式开关（本次拍板新规则）
* **用户故事**：**作为**对记忆措辞准确性要求极高、希望严控所有变更的用户，**我希望**在记忆管理台提供一个“后台整理需我先审批”的开关，**以便**开启后所有涉及合并、修改或删减已有记忆的后台操作都先进入“待审列表”，经我确认后再正式生效。
* **验收标准 (Acceptance Criteria)**：
  1. **Given** 用户在 Workspace 记忆管理台将“后台整理需我先审批”开关切换为【开启】；
  2. **When** 后台任务生成针对已有记忆的合并或修改方案时；
  3. **Then** 原有效记忆保持不变并继续在对话中生效，新方案进入【待审方案】列表；
  4. **Then** 仅当用户点击【批准生效】后才切换为新版本；若审批前原记忆已被用户手动修改，则自动作废旧待审方案并提示重新核对。

### US-08 [P1] L1 核心 + L2 按需检索与时效事实过滤
* **用户故事**：**作为**长期积累了数百条记忆的深度用户，**我希望**每次对话只加载少量核心习惯与当前任务匹配的记忆，并自动区分“上季度负责人”与“现任负责人”，**以便**既不会撑爆模型上下文导致响应变慢变贵，也不会把过时的旧事实当成现状回答。
* **验收标准 (Acceptance Criteria)**：
  1. **Given** 用户积累了大量记忆条目，且包含随时间演进的事实（如项目负责人变更）；
  2. **When** 用户发起具体任务请求时；
  3. **Then** 系统仅注入 L1 核心集合与 L2 任务相关命中项；对含时效的事实默认注入当前有效版本，历史版本仅在追问历史时回读；
  4. **Then** 若针对小模型出现上下文预算不足，优先保留与当前任务强相关的记忆，并在界面“本次使用的记忆”中如实展示未装入提示，绝不静默丢弃或删除底层数据库记录。

### US-09 [新增要求] 按需查询 Project 理解的变化历史
* **用户故事**：作为项目用户，我希望 Agent 能查询项目的重要结论如何变化，以便对照当时与现在的理解及依据。
* **验收标准**：复用已有不可变 `agent_overview_versions` 与 Project agreement/decision `memory_fact_versions`，不建第二份快照或日志表。仅按可信当前 Project 授权查询，以有界分页返回真实时间、身份/版本、前后文本与条件、变化类型及来源指针；忽略时间戳、元数据及纯空白变化。
* 系统只报告原始内容差异，由 Agent 选择有意义的变化；没有显式保存的变更原因就不补写原因。默认不返回原文摘录，原文仍走 L3 授权回读；来源删除不抹去已保存的历史结论。
* 返回显式 `historical: true`，只由按需历史工具读取，不塞入常驻记忆；不读取 Workspace 或其他 Project 的历史正文。当前 head 已遗忘/停用的 fact 历史不返回旧正向内容，旧 Overview 来源仍核验实际 Project 边界。
* 不要求本阶段新增历史 UI；原生服务测试仅证明服务行为，实际 Agent 工具接入与真实使用仍单列验收。

## 4. 记忆生命周期、五种控制操作与冲突裁决规则

### 4.1 记忆生命周期状态定义
每条记忆在系统中由五个正交维度共同描述，不再用一个笼统的“已记住”标签掩盖真实状态：

| 状态维度 | 可选状态值 | 产品行为规则 |
| :--- | :--- | :--- |
| **1. 内容生命周期** | `有效 (Active)` / `已停用 (Disabled)` / `已替代 (Superseded)` / `已遗忘 (Forgotten)` | 默认静默整理的新有效版本直接生效；待审与回退能力属于操作状态，不与事实有效状态混为一列。 |
| **2. 确认程度** | `系统推断 (Inferred)` / `用户已确认 (Confirmed)` | 只有来自真实用户明确指令、手动编辑或回退确认的内容才标记为 `用户已确认`；确认属于具体 revision；后台语义修改后的新版本为推断，不能继承旧版确认或通过重复归纳升级确认。 |
| **3. 来源原文状态** | `原文可回读` / `源文件已移除 (结论仍有效)` | **来源删除不取消结论**；撤权不删除记忆，但被撤权调用方不能经记忆绕过访问范围。归档不等于删除，原文是否可读按实际可用性与授权判断。 |
| **4. 本次对话采用状态** | `本次已注入 (L1/L2)` / `条件未命中 (未带入)` / `可按需回读 (L3)` | 本次对话未带入不代表记忆被遗忘或失效。已实现通过 SDK `conversation.chat.turnTail` 按真实 session / turn / step 查看逐条回答采用的不可变版本，不再仅展示每 Session 最新请求。 |
| **5. 整理操作状态** | `待审` / `已发布` / `24h 可回退` / `已回退` / `已失效` | 审批开关默认关闭；开启时原事实继续生效，方案先待审。回退按原子操作单元核验全部成员 CAS，不能覆盖后来的人工修改或遗忘。 |

### 4.2 五种用户控制操作与源文件删除行为对比

| 操作 / 事件类型 | 用户意图与触发场景 | 底层状态变更 | 生效时间与恢复方式 |
| :--- | :--- | :--- | :--- |
| **1. 局部纠正 (Patch)** | 对话中说“这条不对，日常汇报才极简”或在管理台编辑 | 仅更新目标条目的内容或适用条件并生成新版本；旧版不可变保留为历史，不再作为当前版本采用。 | **下一次模型请求立即生效**；绝不顺手改写其他无关记忆。 |
| **2. 24h 按操作单元回退 (Rollback)** | 对后台静默整理的结果不满意，在 24 小时内点击单条“一键回退” | 以新版本恢复该原子操作的整理前内容并加锁；单条 patch 恢复自身，merge 整组恢复成员与替代关系。 | **提交后下一次模型请求生效**；逐成员 CAS，冲突明确拒绝；同批其他独立操作不变。 |
| **3. 源文件被删除 / 归档** | 用户删除了曾经引用的会议纪要、Record 或本地文档 | **记忆结论保持 `有效` 不变**；实际删除后来源标为 `源文件已移除（不可回读原文）`；仅归档时按真实可用性与授权判断。 | 来源事件本身不使结论退出；用户覆盖/遗忘/停用及既定有效期仍按事实状态判断。 |
| **4. 暂时停用 (Disable)** | 在管理台手动关闭某条记忆的启用开关 | 状态变为 `已停用`，暂停进入 L1/L2 上下文，保留完整内容。 | 下一次请求停止使用；用户随时可在管理台一键重新启用。 |
| **5. 主动遗忘 (Forget)** | 对话中说“忘掉我喜欢极简回答”或管理台点击“主动遗忘” | 状态变为 `已遗忘`，立即退出上下文，并写入**防复生抑制规则**。 | **下一次请求立即剔除**；保留原始聊天记录不删，除非用户未来明确说“重新记住”。 |

### 4.3 冲突裁决优先级（从高到低）
当多条记忆或当前指令出现冲突时，系统严格按以下优先级顺序裁决：
1. **第一优先级：用户主动遗忘与空间权限底线**（已遗忘抑制项绝不加载；跨项目绝不读取其他项目专属约定）。
2. **第二优先级：当前对话的临时明确要求**（如“今天这篇试试活泼风格”，当次回复优先遵从临时指令，但不改写长期偏好）。
3. **第三优先级：最新覆盖的有效记忆 & 本项目专属约定**（新覆盖的结论优先于旧历史版本；本项目 `Project Overview` 约定优先于全局宽泛习惯）。
4. **第四优先级：匹配当前任务场景的全局通用偏好**（带精确场景条件匹配的记忆优先于无条件泛化记忆）。

## 5. 产品入口、管理台交互与标准话术规范

### 5.1 双层产品入口设计
* **Workspace 全局记忆管理台**：
  * **顶部模式栏**：提供 **“后台整理需我先审批”开关**（默认关闭 = 静默自动生效 + 24h 按操作单元回退；开启 = 进入待审方案列表）。
  * **四大筛选标签页**：`有效记忆`、`★ 最近 24h 自动整理（可一键回退）`、`待审方案（开启审批开关时使用）`、`已替代 / 已遗忘`。
  * **单条操作项**：支持展开 `查看依据`、点击 `↺ 24h 一键回退至整理前`、`✎ 用新记忆覆盖`、`暂时停用` 与 `主动遗忘`。
* **Project 项目理解面板 (`Project Overview`)**：
  * 集中展示当前项目的“项目背景与约定”及“阶段决议”，与全局记忆物理隔离。
  * 在对应回答旁展开 **“本次使用的记忆”**，已按真实 session / turn / step 持久记录采用版本，避免后续修改改变旧回答的采用证据。默认 snapshot 与实验 L1/L2 均需区分实际采用及未装入项。

### 5.2 对话端标准回执文案规范
助手在对话中反馈记忆操作结果时，必须简短、可核对，且严格绑定真实落库状态：

| 真实执行结果 | 标准反馈文案模板 |
| :--- | :--- |
| **明确保存成功** | “已保存到 Workspace 记忆：日常汇报先给结论。下次模型请求起使用。” |
| **项目约定保存成功** | “已更新本项目的‘项目背景与约定’：周报使用客户甲合同附件模板。” |
| **局部纠正成功** | “已纠正：日常汇报保持简洁；技术方案分析展开完整推导。其他偏好保持原样。” |
| **24h 按操作单元回退成功** | “已恢复这次整理操作前的内容；本次为[单条修改 / 整组合并]，涉及[实际成员]。下次模型请求起使用。” |
| **源文件删除后询问结论** | “该历史结论依然有效（源文件已移除，无法回读原文段落）。系统会继续按此规则执行，直到你用新规则覆盖或要求忘掉它。” |
| **写入或设置失败** | “本次未保存成功，现有记忆未变。原因：[具体错误说明]。” |

### 6.2 上线前必过评测矩阵（50～100 个中文多轮场景）
在正式将默认加载策略切换为“L1 核心 + L2 按需检索”前，必须在同一模型、同一任务集下完成三组对照实验（① 无记忆基线 vs ② 全量精简快照 vs ③ L1 核心 + L2 按需检索）：

| 评测维度 | 具体考核指标 | 上线通过门槛 (Launch Gate) |
| :--- | :--- | :--- |
| **1. 任务效果与召回率** | 关键偏好命中率、场景条件区分准确率（如日常汇报 vs 技术推导）、中文同义改写召回率（如“先说重点”命中“结论在前”）。 | 任务综合完成质量与偏好命中率**不低于全量精简快照**。 |
| **2. 隔离与确定性边界** | 跨项目约定串台率、主动遗忘后复生率、写入失败虚假承诺率。 | 跨项目误召回率 = `0%`；同源遗忘复生率 = `0%`；虚假回执率 = `0%`。 |
| **3. 源文件删除持久性** | 删除来源文档后，已提炼记忆结论的保持率与正常调用率。 | 来源删除本身导致的结论失效率 = `0%`；主动覆盖/遗忘/停用与既定有效期另按事实状态判断。 |
| **4. 静默整理与 24h 回退** | 默认静默整理准确率、24 小时内原子操作单元回退成功率及下一次请求生效及时率。 | 原子操作回退成功后，下一次模型请求 `100%` 采用恢复内容；单条 patch 独立，merge 全组恢复，不误伤同批其他独立操作。 |
| **5. 成本与性能收益** | 单次请求平均注入记忆 Token 数、首字响应延迟 (TTFT)、后台整理 Token 消耗。 | 相比全量快照，长周期用户单次请求记忆输入 Token 降低 `≥ 35%`，首字延迟不增加。 |


## 7. 本次评审确认与实现契约

2026-10-23 用户明确同意：记忆尚未使用，可重设计底座，不做旧记忆迁移或兼容；Record/File/Todo 等业务数据不能清空。默认静默整理可改变已确认内容的语义，以 24 小时回退兜底，不增加语义审批例外；确认状态属于具体版本，后台写出的新版本标记推断。只有开启审批设置时，后台变更先待审。

- 复用 SQLite、原生事务及 DSH 现有会话/工具机制。事实、不可变版本、原子操作、抑制与提案使用专门模型，不再让知识节点正文兼任记忆权威。
- 稳定 fact_id 与具体 revision 分离；Pending 是变更提案状态，可回退是当前操作的派生能力，二者不与事实 active 状态互斥。
- 停用和遗忘分开；遗忘按事实及证据锚点抑制，不能因同一消息同一类别而误伤另一条独立偏好。跨来源同义重现须真实模型验证，不能以字符串黑名单证明语义抑制。
- 下一次请求包括同一任务工具调用后、旧会话恢复与压缩重建。刷新正向上下文及失效记忆工具结果，不删除用户聊天档案；失效内容不能被当作现行规则。
- L1/L2 正式默认切换前保持预算内精简快照。50～100 中文多轮三组对照使用同一真实模型与相同任务，报告样本、质量、偏好命中、成本和延迟。模型语义评测不能用 mock 替代。
- 来源可用状态逐引用表达；已保存结论不因原文移除而消失。原文回读仍经既有真实来源服务核验。
