## 1. 记忆内容、行为与执行边界

产品中的 Memory 广义包含 Overview 和 Workspace 长期记忆。本文的“长期记忆唯一归 Workspace”约束长期条目，不取消 Project Overview。记忆行为处理交互和任务中的新信息与显式目标更新；整理行为回看资料及已有理解，补全、合并、处理矛盾和过时内容。两种行为都可更新 Overview 或长期记忆，不按产物建立两套行为系统。

| 层次 | 职责与修改边界 |
| --- | --- |
| Context 原生能力 | 保存内容与版本，提供读取、检索和明确操作；核验目标归属、授权、来源、用户决定、CAS、幂等、预算及原子结果 |
| Harness 记忆组件 | 调用 Context 接口组织记忆读取、任务使用和维护；复用 Pi 会话、既有草稿、维护与续跑能力 |
| 一个 Workspace 统一 Skill 文件 | 以“记忆行为”“整理行为”两节表达语义判断方法；各 Project 使用同一版本，不设项目覆盖 |
| Harness 结构化运行设置 | 管理整理开关、频率和时刻，通过工具或脚本实际保存；不能从 Skill 的时间文字自动获得执行权限 |

模型判断内容的稳定性、价值、重复与矛盾；程序核验结构和可信边界，不用关键词、正则或同义词表代替理解，也不另起分类模型。Skill 可编辑的判断方法不能取消入口对应的原生执行保护；来源、版本、权限与实际保存结果由原生层保持。

### 1.1 Skill 与运行设置的调整

用户及具有相应文件修改权限的 Agent 可以直接修改统一 Skill 文件，保留文件变更与版本并告知实际结果；不增加行为草稿确认流程。无权限则拒绝修改。下一次 Provider 请求采用新版本，包括当前 Run 的后续请求；已发出的请求正常结束，不重启。具体文件位置与编辑入口在实施时确定，现有受限 Pi ResourceLoader 不作为已接通的证据。

“记住以后所有汇报先说结论”改变 Context 内容；“以后只记我明确要求保存的信息”改变 Skill。修改行为本身不删除或重写已有记忆，需要整理内容时走明确的 Context 操作。背景、领域、兴趣、方法、偏好、知识入口六类继续作为当前固定分类；调整类别不是本轮新增需求。

“每周日晚上整理，只保留稳定方法”可以同时修改 Harness 设置和 Skill。每周的结构化设置属于本轮目标能力（待接线），不要求新增任意 cron 框架。两项分别核验权限、分别保存；部分失败保留成功项、说明失败原因，重试只处理失败项，不能仅修改文字就声称调度已变。该部分成功规则只适用于行为文件与运行设置，不放宽第 7 节 Overview 与 Workspace 记忆的联合事务。

## 2. 归属、来源与授权

| 内容 | 操作目标 | 生命周期边界 |
| --- | --- | --- |
| 项目目标、进度、阻塞、行动及未决问题 | Project Overview 的对应条目 | 保留当前项目理解、来源及用户纠正；不与 QuickNote 共用正文或保存状态 |
| 项目特有且稳定的背景、方法、技术约束与约定 | Project Overview 的“项目背景与约定”栏目 | 可单独读取和更新；不是独立 Project Memory，项目归档不自动提升为通用记忆 |
| 跨任务稳定背景、明确通用偏好、可复用方法与领域知识 | Workspace 唯一的精简有效长期记忆集合 | 保留六类分类及依据，来源可以属于 Project，但活动条目 owner 只能是 Workspace |
| 长方法、资料、完整讨论与历史过程 | 现有 Record、知识节点与会话历史 | 记忆保存简短结论或入口，不复制成长驻上下文，不自动创建另一份 Record |
| 一次性请求、试探和未采用的模型建议 | 当前会话，必要时为项目待定信息 | 不自动升级为稳定偏好、明确决定或成功经验 |

归属看内容含义，不看它在哪个项目出现。同一来源可支持项目和通用两种结论，但不能把长文本完整复制两份。模型按授权读取相关已有条目后选择补充、替换、合并或零变更，不按标题、类别或来源哈希机械新增。

### 2.1 原始依据与确认程度

每条理解保留真实条目身份、来源、修订、确认程度和有效状态。模型自动形成的条目默认是推断；只有可信用户操作或原生绑定的真实后续用户消息才能形成“用户确认”。用户计划、模型建议、实际成功或失败操作收据各有含义，不能相互替代。保存方案文件只能证明文件保存完成，不证明用户采用了方案。

跨来源合并必须保留完整依据及来源并集。项目归档、原文删除、排除与权限变化仍约束派生记忆；不能删除不方便的引用后继续使用原结论，或通过复制与抽象洗掉依赖。来源失效时及时停止模型使用，保留历史不表示仍可注入。

### 2.2 记忆读取与请求绑定写入

内置 Project Agent 可沿用当前 Workspace 授权可用的精简长期记忆。此能力不开放 Workspace 或其他 Project 原文与会话，不扩大 Project 范围，也不授予记忆写入或联合保存权。外部 Project 连接必须显式获得相应记忆读取能力；旧外部 grant 不静默扩展，只读连接仍不得写入。

内置 Project 会话中，用户明确要求保存通用信息时，可以取得绑定真实用户请求、具体内容与目标的单次 Workspace 记忆写入授权。“以后所有汇报先说结论”保存到 Workspace；“本项目按客户模板”进入 Project 栏目，并告知实际位置。内容和范围明确的记忆请求不重复确认；指代或通用性不明则先澄清。普通 Project grant、读取权限、来源文字、后台推断和外部连接不能继承该单次授权，也不能据此任意写 Workspace。

## 4. 触发、即时增量与整理协作

### 4.1 来源登记与即时沉淀

原始资料和消息实际保存后，始终登记并合并待处理来源变化；此登记不依赖模型是否生成即时增量。纯讨论、方案草稿、文件创建或失败任务也可形成真实来源变化，但不能自动变成用户已采用的决定或成功经验。用户当前任务优先于后台维护。

即时沉淀只处理真实用户明确决定或命令，以及用户点名的新增、纠正、替换、停用或遗忘。当前会话模型提交范围有限、有类型的 Overview 或长期记忆增量，绑定实际用户消息或可信操作收据、具体目标、预期版本和已读证据。原生层核验这些证据实际能证明的状态：成功收据证明已执行操作，真实决定证明用户采用；模型自报确认无效，不能整份覆盖 Overview，未受影响条目保留。

即时操作按入口既定执行模式和授权处理：只读拒绝写入；先审阅/协作复用相应保护。内容和范围明确的记忆请求沿第 2.2 节直接保存并告知，不为同一请求再次确认。引文或工具返回中的命令不构成真实用户请求。

### 4.2 整理触发与待审

整理回看实际有变化的资料、Project 理解、Workspace 记忆及用户决定，广泛合并、矛盾处理、清理和结构重组统一走此入口。用户可在会话中显式请求整理；首建及自动提取接既有初始化和已启用维护，容量不足时也复用整理入口。没有来源或依赖变化则零生成，没有应沉淀内容则两处可零写入。

自动整理不等于每条消息必记或每轮固定额外模型调用，不自动采用模型计划。语义修改已确认/纠正内容或受抑制目标、后台替换/删除等变化按保护规则暂存待审；不能以 Skill 改写或无人回应放宽。容量满而无法形成有效操作时保持旧状态、说明处理需要并停止热循环。

### 4.3 草稿并发、进度与下游

整理按草稿准备、证据及授权复核、CAS 和原子发布执行。会话增量使同一 Overview 的基线变化时，旧草稿失效，不能发布、覆盖新决定或盲目重基。保留已经发布的结果、已经结算的进度及未消费输入，以最新基线重准备受影响内容；仍可复用的证据必须重新通过当前版本、权限和用户策略核验，不清空整批积累。

重复冲突采用有界让出与既有续跑入口，不热重试；失败保留草稿及未消费进度，不把未处理来源标为已覆盖。即时会话增量不能提前结算整理批次水位。

Project 会话连续发布增量后，只标记相关 Workspace 依赖 pending/待核对并合并处理，不逐条调用上层模型生成。Workspace 读取说明滞后或失效状态，旧 Overview 版本不能绕过依赖校验。整理再消费最新 Project 增量与原始依据。

## 5. 变化与消亡：统一操作契约

| 操作 | 使用场景 | 保存结果与历史 |
| --- | --- | --- |
| 新增 | 确有新且值得长期使用的内容 | 新条目及实际来源，不重复已有条目 |
| 替换/纠正 | 事实发生变化或用户纠正原判断 | 同一逻辑条目的新版本；旧版本退出有效集合，保留历史 |
| 合并 | 多条重复或互补，可用一条更清楚地表达 | 保留一个明确目标并写新版本；其余条目标记被替代，保留合并关系与完整依据 |
| 整理删除 | 过时、错误、重复或已失去保留价值 | 从当前有效集合和模型检索中移除；保留历史、操作原因和依据，不物理删除原文 |
| 用户遗忘/停用 | 用户明确要求不再使用或记住 | 移出有效集合，持久保存用户决定和抑制；旧版本及旧会话派生内容不能绕过 |
| 重新启用 | 用户明确撤回某条停用决定 | 仅撤回该决定，重新核对当前依据、权限和容量；不恢复其他停用决定或旧 Run 证明 |

“合并”是面向用户的语义操作，可落成一次原子的 replace 加 remove；不必为了这个词另造通用合并框架。

### 5.1 决定权与确认

- 沿用当前会话已选择的执行模式。需要确认时，以一条自然说明概括本次修改，复用现有方案卡和一次任务确认；按钮和模型理解后的回复共用相同执行入口。
- 自动新增符合规则的推断沿已启用维护授权处理。后台模型提出的语义替换、删除和会减少现有信息的合并，参考 Hermes 先暂存为待审方案；不逐项弹窗，也不靠无人回应视为同意。
- 用户已确认或纠正的记忆不能被无人值守整理覆盖。需要改变时提出具体目标和新内容；明确的新用户决定可以替换旧决定，不能把“受保护”做成永远不可更新。
- 权限失效导致的停止提供是读取规则，不需要等待用户确认；也不等同于模型有权永久删除记录。

### 5.2 清理规则

不设置“30 天未使用就删除”等未经用户要求的过期规则。支持时间和使用情况可以帮助判断，不能代替内容是否仍成立。例：“正在准备考试”在明确考试结束后可以被提议移出；不能仅因一个月没有提起而自行判定结束。

清理关注重复、已被新事实替代、已失去作用的临时背景以及过长条目。语义等价的重述不得伪装成新事实；跨来源重复由模型判断、原生核对目标和来源并集，不再以“同类别+同来源”为唯一身份机制。

合并后的来源必须完整保留。混合授权结论不能删掉不方便的引用继续使用；需用当前可见证据重新形成新结论，不能做来源洗白。若合并涉及已有抑制决定，不得让停用内容随目标变化而复生。

### 5.3 遗忘与原文的区别

整理删除允许未来新的有效信息重新形成理解；用户“不要再记住”必须留下持久抑制。系统至少保留用户所见的目标、决定版本及既有来源/类别抑制，并向后续有权的整理过程提供必要的“不再记住”约束。不得把被遗忘正文重新当作正向记忆注入。

当前原生抑制是同 Workspace、同类别、相同原始来源身份，可能覆盖同一来源中的其他同类候选。界面需如实说明；不宣称能从全库删除所有同义转述。不同独立来源的语义重现由模型结合用户约束判断，仍需真实模型负例验证，不能用字符串黑名单冒充理解。

停用、删除、纠正或被替代的旧版本不能被普通记忆搜索或历史 Run 引用重新带回模型。用户主动查看自己的历史仍沿现有 GUI 历史规则；原始 Record/File/会话不随记忆操作删除。

## 6. 使用：精简有效记忆、按需详细读取

### 6.1 会话快照

有 Workspace 记忆读取权限的会话，在首次真实任务开始时装入完整的、当前授权可见且符合预算的精简有效记忆快照。创建空会话不读正文、不调用模型。快照保留条目身份、版本和确认程度；详细依据沿工具按需回读，不把完整来源附加到提示词。

不再以 node ID 顺序取前八条充当“长期记忆”。八条导航仍可用于普通知识入口；长期记忆需要独立明确的内容预算和精简规则。模型上下文中的记忆与其他系统提示分开标明，记忆文字不是可以覆盖工具权限的指令。

同一快照只在会话上下文中保留一份，不把同一内容每轮再追加成新消息。发给 Provider 的请求通常仍包含当前上下文，因此不承诺每轮零记忆 token 成本，也不依赖所有 Provider 都支持提示词缓存。

### 6.2 更新与失效时机

有效记忆变化时，下一次 Provider 请求使用新快照，包括同一 Run 内的后续请求；普通知识版本变化不要求无关记忆重建。用户纠正、遗忘、撤权和删除的过滤必须在下一轮前生效；已发出的请求正常结束、不重启，不能被假称已使用新记忆；后续写入仍校验最新版本。

继续会话、恢复旧会话和 Pi 压缩后重建上下文，都要复核记忆版本与最新用户策略，不能只刷新新快照而留下旧消息中的失效派生内容。复用现有 Run 来源账本和原生 Pi 会话边界，不另建会话存储。

### 6.3 容量

长期记忆只保存精简事实及知识入口；长方法、教材和大段背景转为已有知识的入口，不自动复制成新 Record。容量计算包含实际记忆文本及封装开销，与系统提示、会话和输出预留合并核对模型可用输入。

需要一个用户可见、可解释的记忆预算设置；其有效值不得超过所选模型扣除必要预留后的能力。**本需求不冻结新的任意字符常量或百分比。** 容量与会话使用功能完成前，须在小/大模型的真实序列化输入上确定并记录可解释默认值、单位和边界；默认值及验证依据是当前交付覆盖 V1/V4 的完成条件，不能留到产品发布后。Hermes 的固定字符数只作为参考，不直接成为产品限制。

超额时先通过明确操作精简；有待确认的整理时保留原有效集合，新内容保持待处理，不假报已记住。切换到更小模型而旧集合放不下时，不任意截断、不再次增加调用次数配额；本轮改为按需记忆检索并明确报告尚未装入完整快照，按实际剩余预算返回结果，不能仍宣称全量记忆已注入。整理完成后再恢复完整精简快照。

长会话的 Pi 压缩和长期记忆精简是两回事，各自受模型输入能力约束。禁止用反复扩大预算或不断丢弃旧内容来掩盖整理失败。

## 7. 一次整理同时更新两处

### 7.1 共同生成与真实证据

联合整理只读取本批真实变化、相关 Project Overview、授权可见的 Workspace 记忆及用户纠正/遗忘约束，不扫描所有项目原文。项目归属与跨任务价值由同一次模型生成判断，输出 Project Overview 操作与 Workspace 记忆操作，两部分各自可为空。每项携带目标与已读证据索引，原生端绑定真实 ID、修订与来源，不接受模型自报权限、用户确认或成功结果。

“一次”指不为两类产物重复生成/分类，不保证工具读取和必要失败恢复合计只产生一次 Provider 请求。已有有效保存草稿恢复不再次生成；草稿因基线变化而失效时，按第 4.3 节重新准备受影响部分，不热循环。

### 7.2 授权与原子发布

联合保存沿既有维护服务核验 Project 与 Workspace 对应授权。没有 Workspace 写权限时，只能将已授权 Project 操作作为明确的单项保存；不能称为双写或在一项已批准联合事务失败后降格部分提交。内置 Project 的明确请求只能取得绑定该次内容的 Workspace 记忆写入权；外部连接和无人值守整理仍沿各自授权核验。

已批准的联合批次在同一 Workspace 数据库内核对两个目标基线、记忆策略版本、当前来源和授权，再在一个原生事务中保存概览、记忆操作、批次结果及处理进度。任一目标冲突、越权或事务失败，两处均不提交，草稿和未消费进度保留。待审期间不提前推进该批已完成水位，其他无依赖任务继续按既有队列处理。

使用既有批次身份、幂等和版本检查；重放返回已保存结果，不生成第二份条目，不另建跨库事务、任务系统或重复日志权威。确认后目标变化时重新核对并展示变化，不能按旧批准覆盖新版本。Skill 与 Harness 设置可以分别成功的规则不适用于此联合发布。

## 8. 存储、历史与初始化

AI 尚未开始用户测试，直接按当前目标实现，不做旧 AI 数据迁入、格式兼容、历史身份映射或开发期 Project Memory 转换器。原有 Record、File、Todo、QuickNote 等业务资料及其含义保持，不以简化 AI 为由清空业务数据库。

复用已有知识正文、不可变版本、来源关系与用户策略，在现有表和 DTO 上最小修改。活动长期 Memory 原生 owner 检查拒绝 Project；稳定项目信息进入可单独读写的 Overview 栏目。新结构建立、保存与重开须一致恢复归属、栏目、版本、纠正和遗忘决定。

停用、纠正、被替代与整理删除保留历史，但退出当前有效模型使用。用户可沿现有 GUI 查看自己的历史；历史存在不等于有效记忆，原始 Record/File/会话不会因记忆操作而删除。

## 9. 操作结果与用户可见状态

Project 知识面板提供“项目背景与约定”，不再单列项目长期记忆。Workspace 记忆入口展示有效条目、依据、推断/用户确认、待审方案及修改或退出原因；行为文件、Harness 设置和 Context 内容是分别可核对的修改目标。

会话按实际保存结果简短说明动作及位置。需要确认的方案以自然业务语言概括，同一任务确认一次，不展示数据库操作清单；明确记忆请求已经足够表达保存意图时直接保存后告知。待审、失败、冲突、预算不足及待核对均如实显示，候选不假报生效。

合并、遗忘和重新启用说明真实作用范围。容量状态区分“当前保存了什么”“本轮实际带入了什么”“需要时还能搜索什么”；后台或配置部分失败不能被笼统成功消息掩盖。

## 10. 验收场景

本表是 #109 的细化验收，使用 ML 编号，不改变既有 A01～A76；对应 A21/A22/A56～58/A64～67/A75。以下均为待执行目标，旧 982 项 Rust 或 27 项前端结果不是这些新场景的通过证据。

| 编号 | 场景 | 必须成立 |
| --- | --- | --- |
| ML01 | 同段话既有项目计划，又有明确通用偏好 | 一次生成分别给出项目和 Workspace 操作；事实、依据不串，调用计数可核对 |
| ML02 | “本项目用客户模板”与“所有日常汇报先说结论” | 前者仅项目栏目，后者 Workspace；随口试探不自动成为偏好 |
| ML03 | 项目里提出通用方法，但没有确认其效果 | 可作为有依据的推断；不擅自扩大适用范围或标用户确认 |
| ML04 | 新增、替换、跨来源合并和整理删除 | 目标版本正确，完整依据和历史保留，退出项不在有效查询中，重放不重复 |
| ML05 | 后台提议修改已确认条目或删除内容 | 暂存待审，旧条目保持；一次自然确认执行，不按关键词匹配，不逐条弹窗 |
| ML06 | 用户纠正后下一轮维护、旧会话恢复与 Pi 压缩重建 | 使用新决定；旧条目、旧 Run 或旧摘要不能重新成为有效依据 |
| ML07 | 用户要求忘记后，同来源换标题/ID再提取；不同来源同义转述 | 同来源原生抑制生效；跨来源模型遵守遗忘约束，以真实模型单独验；不声称全库语义删除 |
| ML08 | 多条停用决定后只重新启用一条 | 只撤回自己的决定；无权/归档来源不恢复模型可见性 |
| ML09 | 完整精简快照、长对话、多轮工具调用 | 同一快照不反复追加；实际请求预算包含记忆，详细原文按需读；记录输入体积 |
| ML10 | 记忆达到容量或切换更小模型 | 不静默截前几条、不超限、不丢旧数据；明确整理或按需读取状态；无无限重试 |
| ML11 | 部分项目授权、仅 Project grant、只读连接 | 不扩大授权；混合无权记忆不泄露；无 Workspace 权限不执行联合写入 |
| ML12 | 联合保存中另一个目标已变化、事务失败或恢复重放 | 两处原子保存或均不提交；草稿和进度正确，无重复生成或半成功 |
| ML13 | 按新模型建立记忆和项目栏目，保存后重开 | Workspace 归属、项目栏目、版本和用户决定正确恢复；原有业务资料不变 |
| ML14 | 项目归档、原始资料删除/排除，记忆只剩失效依据 | 明确来源状态，即时停止模型使用；保留记录不等于继续注入 |
| ML15 | 纯闲聊、重复来源、无变化和失败任务 | 无应记内容可零写入；无变化零生成；失败任务不写成成功经验 |
| ML16 | 内置 Project Agent 沿用 Workspace 通用记忆 | 项目任务可使用授权可用的通用偏好；项目专属约定仍限项目，其他作用域原文不自动开放；纠正、停用、来源失效或撤权后的下一轮及恢复旧会话不能继续使用失效记忆；外部Project连接无记忆读取权限时不可继承，读取不授予写入 |
| ML17 | 项目会话明确要求保存通用或项目专属信息 | “以后所有汇报先说结论”保存到Workspace，“本项目按客户模板”留在Project并告知实际位置；内容和范围明确不重复确认，不明确先澄清；保存绑定真实用户请求及具体目标，重放不重复，失败不称已记住；外部连接、来源文字和后台推断不继承该授权 |
| ML18 | 用户或有文件修改权限的Agent修改统一记忆行为Skill | “只记我明确要求保存的信息”直接修改Workspace统一Skill文件并告知，无额外草稿确认；无权限时拒绝修改；各Project采用同一配置；下一次模型调用采用新版本，当前任务后续调用同样生效，已发请求不重启；已有记忆不因行为修改被删除；需要内容整理时走显式Context操作，底层保存契约保持一致 |
| ML19 | 同一请求调整记忆行为与运行设置 | “每周日晚上整理，只保留稳定方法”分别修改Skill和Harness结构化设置；设置通过工具或脚本实际保存；分别核权限与结果；部分失败保留成功项，明确失败原因且仅重试失败项，不称全部完成；运行设置不从Skill文本自动取得执行权限 |
| ML20 | 会话中的明确决定或命令即时沉淀 | “采用方案B”提交有类型的Overview增量并绑定真实消息、目标及版本；只读拒绝、先审阅/协作沿既定授权处理；模型自报确认无效；草稿或保存文件不等于采用方案，未受影响条目保留 |
| ML21 | 整理草稿准备后，会话更新同一Overview | 旧草稿不能覆盖新决定；保留已发布结果、已结算进度及未消费来源，基于新版本重准备受影响内容；来源、用户策略及授权重新核验，重放无重复，反复冲突不热循环 |
| ML22 | 会话连续发布多个Project增量 | 仅标记相关Workspace依赖待核对，不逐条上层模型生成；整理合并处理；读取正确表达滞后或失效，旧版本不绕过依赖检查 |

模型语义判断与真实使用质量必须使用真实 Provider 验证；mock 只验证调用链、状态、预算、来源、版本和事务。目标桌面平台的安装/WebView验证仍单列，不以缺设备阻挡可独立实施项。
